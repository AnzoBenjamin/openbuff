## [HIGH] error-handling — packages/agent-runtime/src/tools/stream-parser.ts:782 — Class A (GAP): streaming XML tool-call parse errors (invalid_tool_call_json, missing_tool_name) never reach the model's next-turn prompt
- **Risk:** Observed path: a malformed codebuff_tool_call block is detected by parseToolCallContent (stream-xml-parser.ts:253-309), which emits invalid_tool_call_json (messages at 262, 276, 303) or missing_tool_name (291) instead of a tool call. emitParserErrors (tool-stream-parser.ts:194-201, invoked at 213) forwards each error ONLY through the onResponseChunk callback — it is never yielded into the stream. The wrapper processStream hands to processStreamWithTools (tools/stream-parser.ts:758, callback at 777-790) hits the explicit `else if (chunk.type === 'error') { // do nothing }` branch at 782-783: no push to assistantMessages, no push to errorMessages, no hadToolCallError, and the consumption loop's error branch (848-858, which DOES record) never fires because the error was never yielded. The finally block (867-952) therefore appends no TOOL_CALL_ERROR user message (errorMessages spread at 949-950), and the malformed block itself was already stripped from filteredText — the persisted assistant message is built from filtered text only (778-781). What the model sees next turn (messages: agentState.messageHistory, run-agent-step.ts:1042): its own non-tool text, no tool call, no error, no raw payload. It cannot distinguish 'call dropped' from 'call succeeded', so it can repeat the identical malformed shape indefinitely — a silent degeneration loop. Contrast: executor-emitted tool errors (validation failures inside executeToolCall) DO self-correct, because they flow through responseHandler (685/706) into createResponseHandler (287-304) which sets hadToolCallError and pushes the TOOL_CALL_ERROR user message that the finally block persists.
- **Fix:** In tools/stream-parser.ts:782-783 replace the do-nothing branch with the exact handling createResponseHandler (287-304) and the loop branch (848-858) already use: set hadToolCallError = true and errorMessages.push(userMessage({ content: withSystemTags(`Error during tool call: ${chunk.message}. Please check the tool name and arguments and try again.`), tags: ['TOOL_CALL_ERROR'] })). That single change routes Classes A and B into messageHistory via the existing finally block (949-950) and repairs the turn-control aggravator (see the hasNoToolResults finding). Optionally include a bounded excerpt of the malformed content (see the raw-content finding) so the model can diff its JSON instead of guessing.
- **Evidence:** Verified chain: stream-xml-parser.ts:27 (StreamParserError code union), 253-309 (parseToolCallContent error sites at 262/276/291/303), tool-stream-parser.ts:194-201 + 213 (emitParserErrors callback-only), tools/stream-parser.ts:758 (wrapper), 777-790 (onResponseChunk with do-nothing at 782-783), 848-858 (loop error branch), 867/949-950 (finally appends errorMessages), 958-965 (returns hadToolCallError), run-agent-step.ts:1042 (messages: agentState.messageHistory). Executor contrast: responseHandler wiring at 685/706 -> createResponseHandler 287-304; pinned by __tests__/tool-validation-error.test.ts:738-742 (hadToolCallError true for executor errors). Model-visibility nuance: util/agent-output.ts:9-15 strips the TOOL_CALL_ERROR tag only from parent-visible agent output, NOT from the model's own next-turn prompt. CLI side: cli/src/utils/message-history.ts has zero matches for type==='error'/PrintModeError/hasError (not persisted); cli/src/utils/message-block-helpers.ts:1392-1397 can render {type:'error'} objects but cli/src/hooks/use-chat-streaming.ts has no error-chunk branch (its only 'error' match, line 173, is an unrelated new Error), so parser errors are display-only at best.

## [HIGH] error-handling — packages/agent-runtime/src/util/stream-xml-parser.ts:196 — Class B (GAP): tool_call_buffer_exceeded silently discards the oversized tool call; the model never learns it was dropped and the payload is unrecoverable
- **Risk:** Observed path: when buffered tool-call content exceeds maxToolCallBufferLength (64 KiB default), parseStreamChunk pushes { code: 'tool_call_buffer_exceeded', message: 'Discarded unterminated codebuff_tool_call content after N buffered characters (limit M). Discarding content until the end tag.' } (stream-xml-parser.ts:196-201) and enters discardingUntilEndTag (202-205), consuming everything up to and including the end tag silently so nothing leaks into the text stream. The error then follows the exact Class A route — emitParserErrors -> the wrapper's do-nothing branch — so it is UI-only: no errorMessages entry, no hadToolCallError, nothing in messageHistory. Worse than A, the payload is destroyed by design: state.buffer is reset to a partial-tag carry (203-204), it is never parsed, never yielded, never logged, and filteredText/fullResponse contain only the surrounding text (tools/stream-parser.ts:101 and 847 record filtered chunks). What the model sees next turn: no evidence the call ever existed. It cannot distinguish 'the call was dropped for being oversized' from 'the call succeeded', and the overflow cause (oversized payload, often a max-token truncation mid-call) is invisible, so it cannot choose between shortening the payload and retrying as-is. Verdict: GAP — the model never learns its tool call was dropped; the content is unrecoverable.
- **Fix:** The wrapper fix from the Class A finding (tools/stream-parser.ts:782-783) covers B's transcript gap. Additionally, for B specifically: emitParserErrors (tool-stream-parser.ts:194-201) should forward the structured code/bufferedLength/maxBufferLength fields (already on StreamParserError, stream-xml-parser.ts:199-200) instead of message text only, so the wrapper can append actionable recovery guidance — the call exceeded the 64 KiB buffer, split the payload or write content to a file instead of inlining it. Given overflow is frequently caused by a max-token cut mid-call, also consider correlating with the providerReportedTruncation evidence the executor already classifies.
- **Evidence:** stream-xml-parser.ts:196-205 verified verbatim: errors.push({ code: 'tool_call_buffer_exceeded', message: 'Discarded unterminated codebuff_tool_call content after N buffered characters (limit M). Discarding content until the end tag.', bufferedLength, maxBufferLength }) then state.discardingUntilEndTag = true and state.buffer reduced to a partial-end-tag carry; the discard-mode scan (106-137 area) consumes the end tag silently by design. DEFAULT_MAX_TOOL_CALL_BUFFER_LENGTH = 64*1024 (module constant at top of file). Emission route identical to Class A: tool-stream-parser.ts:213 -> tools/stream-parser.ts:782-783 do-nothing. code_search for tool_call_buffer_exceeded across packages/agent-runtime/src returns only the parser, its type, and its tests — no other consumer records it.

## [HIGH] error-handling — packages/agent-runtime/src/run-programmatic-step.ts:1179 — Class C (GAP): parse_error segments in programmatic steps are streamed to the client but never written to messageHistory, so the model transcript omits them
- **Risk:** Observed path: in the STEP_TEXT branch (run-programmatic-step.ts:636-649), generator-authored text is parsed by parseTextWithToolCalls (util/parse-tool-calls-from-text.ts:58-131), which emits parse_error segments at 95 ('did not parse to a JSON object.'), 111 (MISSING_TOOL_NAME_REASON) and 118 ('JSON parsing failed: ...'). executeSegmentsArray (1163-1190) handles text by pushing assistantMessage into agentState.messageHistory (1174-1175) and streaming it (1178), but handles parse_error ONLY via onResponseChunk({ type: 'error', message }) at 1179-1180: no messageHistory write, no agentState.output field, no tool result, nothing queued through addProgrammaticToolResultContext. The surrounding text segments land in the transcript while the malformed block and its parse failure do not — the raw block is sliced out by the extraction pattern, and executeSingleToolCall (918) is never invoked for it. What the model sees next turn: its text with a silent hole where the tool call was. Contrast within the SAME file: the runProgrammaticStep catch block does transcript errors correctly — onResponseChunk(errorMessage) at 746 AND agentState.messageHistory.push(assistantMessage(errorMessage)) at 751-753 — and executed programmatic tools reach the transcript via formatProgrammaticToolResultMessage (859) + the pending-context flush. Only parse failures are swallowed. Verdict: GAP — the message is streamed to the client but never becomes transcript text the model can see.
- **Fix:** In executeSegmentsArray (run-programmatic-step.ts:1179-1180), after onResponseChunk also write the failure into the transcript — either via the existing addProgrammaticToolResultContext seam (its flush appends user context into agentState.messageHistory) or directly: agentState.messageHistory = [...agentState.messageHistory, userMessage({ content: withSystemTags(segment.message), tags: ['TOOL_CALL_ERROR'] })]. Additionally extend ParsedToolCallParseError (util/parse-tool-calls-from-text.ts) to carry a bounded raw excerpt of the offending block and include it in that message, so the model can correct the JSON rather than guess — mirroring the executor's self-correcting 'Original tool call input' pattern.
- **Evidence:** run-programmatic-step.ts:636-649 (STEP_TEXT -> parseTextWithToolCalls), 1163-1190 (executeSegmentsArray; text push 1174-1175, parse_error stream-only 1180, tool_call 1183); parse-tool-calls-from-text.ts error sites 95/111/118 and ParsedToolCallParseError carrying only {type, message}; catch-block contrast at 746 and 751-753; formatProgrammaticToolResultMessage at 859; executeSingleToolCall at 918. The transcript channel demonstrably exists and is used for every other error in this file.

## [MEDIUM] correctness — packages/agent-runtime/src/run-agent-step.ts:1196 — Aggravator: parser errors never set hadToolCallError, so a malformed-only response can silently end the turn instead of retrying
- **Risk:** Observed path: hasNoToolResults (run-agent-step.ts:1196-1203) deliberately forces another step when hadToolCallError is true — 'Tool call errors should also force another step so the agent can retry' (1203). Because Classes A/B never set the flag (hadToolCallError is written only by createResponseHandler at tools/stream-parser.ts:291 and the loop branch at 850, both unreachable for parser errors), a response consisting solely of one malformed codebuff_tool_call yields hasNoToolResults = true. For agents without task_completed, shouldEndTurn = hasNoToolResults && !isThinkOnly (1242) then ENDS the turn: zero user-visible work, zero transcript feedback, no retry. For explicit-completion templates the turn continues, but with no error in context the model has no signal not to repeat the identical malformed call. Verdict: GAP (aggravator) — the retry safety net exists and works for executor errors but is not armed for parser errors.
- **Fix:** No change needed in run-agent-step.ts itself: setting hadToolCallError in the wrapper fix (tools/stream-parser.ts:782-783, Finding 1) automatically makes hasNoToolResults false, forces the retry step, and gives that retry the TOOL_CALL_ERROR context it currently lacks.
- **Evidence:** run-agent-step.ts:1196-1203 (hasNoToolResults with `!hadToolCallError` and the retry comment at 1203), 1233-1243 (shouldEndTurn; explicit-completion vs default), tools/stream-parser.ts:291 and 850 (the only two hadToolCallError writers, both unreachable for parser errors), 958-965 (return). hasNoToolResults is computed from processStream's return value, so fixing the emission site fixes this with no change to run-agent-step.ts.

## [MEDIUM] error-handling — packages/agent-runtime/src/tool-stream-parser.ts:194 — Raw malformed content is preserved nowhere the model can see in any failure class, so even an error notice would leave the model unable to diff its broken JSON
- **Risk:** Observed path: across all three failure classes the malformed bytes are irrecoverable. (A) parseToolCallContent (stream-xml-parser.ts:253-309) parses then discards; StreamParserError (27-35) carries only code/message/bufferedLength/maxBufferLength — never the content. (B) the overflow discard (196-205) intentionally destroys the buffer. (C) parse_error segments carry only a message; TOOL_EXTRACTION_PATTERN strips the whole block from the surviving text segments. The persisted assistant messages contain only filteredText (tools/stream-parser.ts:778-781) and fullResponse only filtered chunks (101, 847); emitParserErrors (tool-stream-parser.ts:194-201) drops the structured code and bufferedLength/maxBufferLength fields too, forwarding message text alone. Consequence: even after fixing the transcript routing (Findings 1-3), an error notice without the offending bytes still leaves the model to guess which of possibly several tool calls in one response was the malformed one and what was wrong with it. Contrast: the executor path DOES quote raw input back to the model — error messages include 'Original tool call input:' excerpts — which is exactly why executor errors self-correct and parser errors cannot. Verdict: GAP — raw content is preserved nowhere the model can see, in any class.
- **Fix:** Extend StreamParserError (stream-xml-parser.ts:27-35) and ParsedToolCallParseError (util/parse-tool-calls-from-text.ts) with a bounded rawExcerpt field (e.g. first/last 500 characters around the failure point, hard-capped so a 64 KiB overflow cannot balloon the transcript), populate it at every error site, and include it in the TOOL_CALL_ERROR user message produced by the wrapper fix from Finding 1. This mirrors the executor's already-proven self-correcting shape.
- **Evidence:** stream-xml-parser.ts:27-35 (StreamParserError shape — no content field); parse-tool-calls-from-text.ts (ParsedToolCallParseError = {type, message} only; error sites 95/111/118); tools/stream-parser.ts:778-781 (assistantMessages from filtered text) and 847 (fullResponseChunks from filtered text); executor contrast pinned by __tests__/tool-validation-error.test.ts:3756-3761 (error message must contain 'Parsing as JSON failed:' and 'Original tool call input:').
