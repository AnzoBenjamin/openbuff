## [HIGH] security — sdk/src/provider-config.ts:1002 — Ancestor openbuff.json files override the project's own config, letting a parent-directory config re-route models and exfiltrate apiKeyEnv secrets
- **Risk:** getDefaultProviderConfigPaths emits [configDir files, cwd/openbuff.json, parent/openbuff.json, ...] and loadProviderConfigSync merges in that order with mergeProviderConfigs making the LATER file win. A parent-directory openbuff.json (inside the home-bounded ancestor walk, MAX_ANCESTOR_SCAN_DEPTH=10) therefore overrides the project's own providers/defaultModel/modes/agents. It can re-point the effective provider baseURL at an attacker-controlled HTTPS endpoint while apiKeyEnv still sources the user's real secret into the Authorization header, so every model request leaks the env secret to the attacker. run.ts's readableRoots comment asserts the opposite precedence ('a non-empty project value WINS the merge'), so consumers cannot even rely on the documented behavior.
- **Fix:** Reverse precedence so the config nearest cwd wins over ancestor files (or only allow ancestors to ADD providers, never override project routes), and require an explicit opt-in (like OPENBUFF_TRUST_ANCESTOR_CONFIG) before an ancestor config may declare apiKeyEnv providers or contribute routes. Align the run.ts comment with whatever precedence is kept.
- **Evidence:** sdk/src/provider-config.ts:1002 getDefaultProviderConfigPaths returns [...configDir paths, ...getAncestorProviderConfigPaths(process.cwd())]; getAncestorProviderConfigPaths pushes path.join(currentDir, PROVIDER_CONFIG_FILE_NAME) starting at cwd then walks UP, so parent entries come AFTER the project's own file. loadProviderConfigSync loops configPaths in order doing config = mergeProviderConfigs(config, parsedConfig.config) where the second argument is the override (later wins) for providers/defaultModel/modes/agents. warnIfAncestorConfigHasApiKeyEnv (provider-config.ts:1057) only prints a console warning and the config is still loaded.

## [HIGH] security — sdk/src/run.ts:2336 — Project-supplied fileChangeHooks execute repo-controlled shell without the high-impact approval gate applied to run_terminal_command
- **Risk:** fileChangeHooks commands come from openbuff.json (repo-controllable in a cloned repository) and runFileChangeHooks executes them whenever the agent calls run_file_change_hooks after editing files. The dispatch branch passes only {files, cwd, env, signal, fileSystem} - no classify/authorizeHighImpactAction/approvalService - so hook commands bypass evaluateHarnessActionPolicy and the approval receipt flow that run_terminal_command enforces for push/commit/dependency-install. A malicious repo can therefore run arbitrary shell (exfiltration, persistence) through what is presented as a routine verification gate. autoFileChangeHooks only gates manifest-inferred hooks, not explicitly declared ones.
- **Fix:** Route hook commands through the same classify-and-approve pipeline as run_terminal_command (or run them under a restricted permission profile), and require an explicit trust opt-in for project-supplied hooks the way readableRoots/ancestor-config trust is gated.
- **Evidence:** sdk/src/run.ts:2336 dispatches runFileChangeHooks({files, cwd: requireCwd(...), env, signal, fileSystem: fs}) with no approval hook, while the run_terminal_command branch (run.ts ~2130) threads authorizeHighImpactAction -> evaluateHarnessActionPolicy + HarnessApprovalService.consume. sdk/src/provider-config.ts fileChangeHooks comment: 'Commands run by the run_file_change_hooks tool after the agent edits files (e.g. typecheck/lint/test) - the verification gate.'

## [HIGH] security — sdk/src/provider-config.ts:1057 — Cloned-repo openbuff.json can declare an apiKeyEnv provider pointing at an attacker endpoint with no trust gate at all
- **Risk:** openAICompatibleProviderSchema permits any https baseURL with apiKeyEnv; resolveConfiguredProviderModel then puts env[apiKeyEnv] into the Authorization header sent to that baseURL. For a config file INSIDE the project (a cloned repository's openbuff.json) no warning or acknowledgement exists at all: warnIfAncestorConfigHasApiKeyEnv explicitly excludes project files (resolved under projectRoot) from its warning set. Running openbuff inside a malicious repo with, say, OPENAI_API_KEY set silently sends that key to the repo author's server on the first model request.
- **Fix:** Apply the same acknowledgement model used for readableRoots to project-supplied providers that source secrets from env (e.g. OPENBUFF_TRUST_PROJECT_PROVIDERS=1 or per-provider confirmation in /setup), and warn (or refuse) when a non-config-dir config declares apiKeyEnv, not just ancestor ones.
- **Evidence:** sdk/src/provider-config.ts:1057 warnIfAncestorConfigHasApiKeyEnv computes ancestorPaths = sourceFilePaths.filter(p => resolved !== projectRoot && !resolved.startsWith(projectRoot + path.sep)) - project files are filtered OUT, so a repo's own openbuff.json never triggers the warning. resolveConfiguredProviderModel (provider-config.ts) throws only when the env var is MISSING; when present it returns apiKey: env[provider.apiKeyEnv] for any matching provider regardless of which file declared it.

## [MEDIUM] security — sdk/src/run.ts:2274 — browser_logs trusts a model-supplied _browserOwner session identity instead of injecting the runtime-owned owner
- **Risk:** Every process-job tool overrides model-supplied owner with the trusted runtime owner (check_job/kill_job/read_logs/list_jobs comments state 'the trusted owner overrides any model-supplied owner'). browser_logs instead reads _browserOwner straight from the tool input and only checks presence. ## [MEDIUM] correctness — sdk/src/impl/chatgpt-backend-fetch.ts:355 — Tool-call argument reassembly emits the FULL final arguments on top of already-streamed deltas when they do not prefix-match, corrupting tool input
- **Risk:** In both response.function_call_arguments.done and response.output_item.done, when doneArguments does not start with the accumulated previousArguments, missingSuffix is set to the entire doneArguments and streamed as an additional delta. The downstream consumer already received previousArguments, so the final tool arguments become previousArguments + doneArguments (malformed JSON) instead of the final arguments. The tool call then fails schema validation or executes with mangled input on the ChatGPT OAuth path.
- **Fix:** On prefix mismatch, replace rather than append: either emit a corrected complete tool-call chunk with the authoritative arguments (and have the consumer replace), or track the true diff and resend only it; add SSE fixture tests with out-of-band/rewritten done arguments.
- **Evidence:** sdk/src/impl/chatgpt-backend-fetch.ts:355-360 and 389-394: const missingSuffix = doneArguments.startsWith(previousArguments) ? doneArguments.slice(previousArguments.length) : doneArguments; if (missingSuffix) { outputIndexToArguments.set(outputIdx, doneArguments); ... emit(... function: { arguments: missingSuffix }) } - in the else branch missingSuffix === doneArguments, appended on top of deltas already emitted via response.function_call_arguments.delta.

## [MEDIUM] correctness — sdk/src/impl/llm.ts:134 — Token/cost accounting has no cache-write or reasoning split, so BYOK cost and cache-debug usage misprice cache writes and hide reasoning spend
- **Risk:** UsageTokenCounts only carries inputTokens/outputTokens/cachedInputTokens (treated purely as cache reads). ## [MEDIUM] correctness — sdk/src/run.ts:2622 — extractStatusCodeFromMessage classifies status codes by bare substring match, so unrelated text (e.g. '1500ms') yields a wrong public statusCode
- **Risk:** The heuristic does errorMessage.includes('500'), includes('429'), includes('408') etc. on the raw message: a message containing '1500ms' or a job id with '429' inside it is misclassified as HTTP 500/429, and any 'timeout' wording becomes 408. The value is written into the public RunState output statusCode field via handlePromptResponse, so hosts and retry logic downstream act on a fabricated status (e.g. treat a bug message as a retryable 503).
- **Fix:** Prefer structured status sources first (extractApiErrorDetails / getErrorStatusCode) and only fall back to anchored regexes such as /\b(?:status|http)\s*(4\d\d|5\d\d)\b/ or /\b(408|429|500|502|503|504)\b/ instead of bare includes().
- **Evidence:** sdk/src/run.ts:2622-2686: if (errorMessage.includes('503') || lowerMessage.includes('service unavailable')) return 503; ... if (errorMessage.includes('504')) ... if (errorMessage.includes('500')) return 500; if (errorMessage.includes('429') || ...) return 429. Called from handlePromptResponse which spreads statusCode into the resolved RunState output.

## [MEDIUM] error-handling — sdk/src/impl/llm.ts:1496 — No first-token/stall/chunk timeouts on the LLM stream: a stalled provider hangs the run because runTimeoutMs defaults to disabled
- **Risk:** promptAiSdkStream awaits response.finishReason and the fullStream iterator with no per-phase deadlines; awaitOptionalPostStreamMetadata bounds only the 500ms post-stream metadata. ## [MEDIUM] error-handling — sdk/src/run-state.ts:253 — Git hydration subprocesses have no timeout and buffer stdout unboundedly, and they run before run.ts arms any timeout
- **Risk:** childProcessToPromise attaches data handlers that do `stdout += data.toString()` with no maxBuffer and never kills the child; getGitChanges runs four git commands (status/diff/diff --cached/shortlog) during initialSessionState. A wedged git (index lock, network fs hang, credential prompt) blocks run() indefinitely, and a huge diff is buffered fully into memory and then into every session state sent to providers. Because runOnce arms runSignal/runTimeoutMs only AFTER `await initialSessionState(...)`, the documented run timeout cannot bound this phase at all.
- **Fix:** Add a per-command timeout + maxBuffer cap to childProcessToPromise (kill the child and return '' on timeout), truncate captured diffs, and arm the run timeout/watchdog before session hydration (or run hydration under its own AbortSignal).
- **Evidence:** sdk/src/run-state.ts:253-283 childProcessToPromise: `proc.stdout?.on('data', (data: Buffer) => { stdout += data.toString() })`, resolve on close, no timeout/kill; getGitChanges awaits these inside initialSessionState. sdk/src/run.ts runOnce ordering: `sessionState = await initialSessionState(...)` executes before `const timeoutAbortController = new AbortController()` / `timeoutHandle = setTimeout(...)`.

## [MEDIUM] correctness — sdk/src/impl/llm.ts:1184 — experimental_repairToolCall echoes malformed tool input back un-repaired (only agent-alias repair exists), so invalid input is re-dispatched instead of repaired or dropped
- **Risk:** The repair hook only rewrites NoSuchToolError calls matching spawnable/local agents into spawn_agents; for every other malformed call it logs 'passing through for graceful error handling' and returns the ORIGINAL toolCall.
