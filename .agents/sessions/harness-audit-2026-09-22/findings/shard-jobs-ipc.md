## [CRITICAL] correctness — packages/agent-runtime/src/tools/handlers/tool/check-background-agent.ts:314 — check_background_agent returns a bare json block where CodebuffToolOutput is a 1-tuple array — all three return sites hide the shape break with `as unknown as`, making every result unrenderable at runtime
- **Risk:** CodebuffToolOutput is z.tuple([{type:'json',value}]) (common/src/tools/params/utils.ts:831-839) — an ARRAY. ## [HIGH] correctness — sdk/src/tools/check-job.ts:198 — check_job deadline math trusts schema validation: a non-finite/oversized timeout_seconds yields a NaN deadline and an infinite hot-spinning follow where kill_on_timeout can never fire
- **Risk:** resolveCheckJobWaitBounds computes `const timeoutMs = Math.max(0, (params.timeoutSeconds ?? 0) * 1000)`; for a non-numeric or coerced timeout_seconds (models emit "30", null, or junk through non-validating paths) this is NaN (Math.max(0,NaN)=NaN) and deadline=NaN. Then `Date.now() >= deadline` in the loop-exit test (line 543 region) is always false so the follow never ends via deadline, `timedOut = timeoutMs > 0 && ...` is false so kill_on_timeout never triggers, and `jobRegistry.wait(jobId, { timeoutMs: Math.min(POLL_INTERVAL_MS, remaining) })` (line 562) passes NaN to setTimeout, which fires immediately — turning the follow into a CPU hot loop that only ends when the job settles (possibly never). Unlike resolveCheckBackgroundAgentWaitBounds (check-background-agent.ts) there is no Number.isFinite guard, no default follow bound and no 600s cap, so an oversized value can also hold the turn far beyond the documented maximum.
- **Fix:** Mirror the hardened resolveCheckBackgroundAgentWaitBounds: treat non-finite/negative timeoutSeconds as omitted, clamp every deadline to [0, 600]s, give follow mode a finite default (e.g. 30s) deadline, and clamp the wait timeout to a finite non-negative number before passing it to jobRegistry.wait.
- **Evidence:** sdk/src/tools/check-job.ts:198-202 resolveCheckJobWaitBounds `{ const timeoutMs = Math.max(0, (params.timeoutSeconds ?? 0) * 1000); return { timeoutMs, deadline: Date.now() + timeoutMs } }`; called at :333; exit test `if (matched || finished || Date.now() >= deadline)`; `const timedOut = timeoutMs > 0 && !matched && !finished && ...` (NaN > 0 === false); :562 `await jobRegistry.wait(jobId, { timeoutMs: Math.min(POLL_INTERVAL_MS, remaining), cursor })`. Contrast packages/agent-runtime/src/tools/handlers/tool/check-background-agent.ts resolveCheckBackgroundAgentWaitBounds (Number.isFinite guard, DEFAULT_CHECK_BACKGROUND_AGENT_FOLLOW_TIMEOUT_MS = 30_000, MAX_CHECK_BACKGROUND_AGENT_FOLLOW_TIMEOUT_MS = 600_000 cap), whose own doc comment cites 'a caller that reaches this handler through a non-validating path'.

## [HIGH] state-mutation — sdk/src/tools/background-jobs.ts:999 — Recovered jobs never settle: the fake ChildProcess gets no exit/error handlers and nothing re-checks pid liveness, so a recovered job whose process dies later reads 'running' forever
- **Risk:** recoverBackgroundJob returns `child: { pid: metadata.processId ?? undefined } as ChildProcess` (line 999) with no listeners, and settleBackgroundJob is reachable only from live-child 'exit'/'error' handlers or killBackgroundJob. The 'lost' promotion at recovery time only covers a pid that is ALREADY dead when recovered. A job recovered while alive that later exits stays 'running' indefinitely: jobSettled (check-job.ts:31) never turns true, so every check_job follow burns its full timeout and never reports an exitCode; list_jobs shows it running forever (affecting the digest fingerprint gate too) and end_turn warns about it every turn. This is one of the two reported 'check_job is broken in practice' symptoms.
- **Fix:** On each observation (check_job poll / list_jobs / a lazy sweep) of an adapter without a live ChildProcess, re-verify pid liveness plus the captured /proc starttime and, when the process is gone, do a final readNewJobOutput drain and fold a terminal lifecycle ('completed' when the log shows clean completion is undeterminable — else 'lost'). Alternatively run a periodic liveness sweep over recovered adapters.
- **Evidence:** sdk/src/tools/background-jobs.ts:935 recoverBackgroundJob; :999 `child: { pid: metadata.processId ?? undefined } as ChildProcess`; :966-970 region promotes to 'lost' only when the pid is dead AT recovery; child.on('exit')/child.on('error') handlers are registered only in startBackgroundJob (live spawns); killBackgroundJob (:1088) is the only other settle path.

## [HIGH] correctness — sdk/src/tools/background-jobs.ts:1167 — kill_job settles 'stopped' on signal delivery with no exit confirmation and no SIGKILL escalation, contradicting the documented kill contract (leaked process + false terminal receipt)
- **Risk:** killBackgroundJob settles the job 'stopped' (line 1167) immediately after terminateProcessTree/killProcess returns true (lines 1134/1158) — i.e. when the signal is DELIVERED, not when the process exits. A child that ignores SIGTERM (or is in uninterruptible I/O) keeps running and appending to its log while check_job/list_jobs report 'stopped' with do_not_repoll, and read_logs/check_job tail keep showing new bytes for a 'stopped' job. The agent-runtime handler documents 'process-group SIGTERM with SIGKILL escalation' (packages/agent-runtime/src/tools/handlers/tool/kill-job.ts:18-20) and the kill_job schema says 'use SIGKILL only if graceful termination fails', but no escalation path exists anywhere in the adapter.
- **Fix:** Fold the registry's existing 'stopping' state on signal delivery and settle 'stopped' only from the child 'exit' event; add bounded SIGKILL escalation (e.g. 5s after SIGTERM, or on the next observation where isProcessTreeAlive still reports true) and report `killed: true, status: 'stopping'` until exit is observed.
- **Evidence:** sdk/src/tools/background-jobs.ts:1088 killBackgroundJob; :1134 `killed = terminateProcessTree(job.child, signal)`; :1158 `killed = killProcess(...)` (recovered path); :1165-1167 `if (killed) { settleBackgroundJob(job, 'stopped', job.exitCode) }` — settle before any exit event; the later child 'exit' handler is absorbed by the registry's terminal states. packages/agent-runtime/src/tools/handlers/tool/kill-job.ts:18-20 doc claim of 'SIGKILL escalation' has no implementation.

## [HIGH] security — packages/agent-runtime/src/tools/handlers/tool/check-background-agent.ts:199 — check_background_agent confirms existence of foreign jobs ('not owned by this client session/root run') while check_job/kill_job deliberately blur existence — a cross-session job-id oracle
- **Risk:** The `foreign` branch returns a distinct message (lines 196-200), telling any caller that the id EXISTS but belongs to someone else. sdk/src/tools/kill-job.ts:26-44 deliberately returns the SAME generic not-found for foreign 'so the caller cannot probe for other sessions' jobs', and check_job (sdk/src/tools/check-job.ts ownership gate) does the same. Background agent ids are `bg-agent-job-<counter>-<8 hex of Math.random()>` (background-agent-jobs.ts allocateBackgroundAgentJobId) — counter-ordered with only 32 bits of entropy — so on the shared local runtime an agent can cheaply enumerate ids and use this oracle to learn about other sessions'/runs' live background agent activity (timing, existence, churn).
- **Fix:** Return the identical generic not-found payload for both `not_found` and `foreign` (jobNotFoundMessage) and route the distinction to a server-side log/metric only. Optionally increase id entropy to >=128 bits so enumeration is infeasible even with an oracle.
- **Evidence:** check-background-agent.ts:188-201 `owned.reason === 'not_found' ? { jobId, errorMessage: jobNotFoundMessage(jobId) } : { jobId, errorMessage: 'Background agent job is not owned by this client session/root run.' }` (message at :199). sdk/src/tools/kill-job.ts:26-44 comments + identical `No background job found with id ...` for both unknown (:28) and foreign (:43). background-agent-jobs.ts:73-78 id shape `bg-agent-job-<counter base36>-<Math.random().toString(16).slice(2,10)>`.

## [MEDIUM] error-handling — sdk/src/job-update-forwarder.ts:95 — job_update forwarding fires handleEvent with `void` — a rejecting async host handler becomes an unhandled rejection, with no backpressure or drop accounting
- **Risk:** `void handleEvent({...})` (line 95) neither awaits nor catches, and handleEvent is typed `void | Promise<void>`, so a transport write failure rejects unhandled (fatal under throw-on-unhandledRejection configurations) and the event is silently lost. Because this listener runs on EVERY registry emit (subscribeAll) with no queue bound, a slow or stalled host accumulates unbounded pending promises behind a chatty job's 250ms drainer — unbounded memory growth and eventual event reordering at the host.
- **Fix:** Wrap in `Promise.resolve(handleEvent(ev)).catch(...)` with an error counter, add a bounded forward queue with a documented drop policy, and surface dropped-update counts (e.g. as a status event) so the UI never silently loses job activity.
- **Evidence:** sdk/src/job-update-forwarder.ts:60-110 createJobUpdateForwarder; :95 `void handleEvent({ type: 'job_update', ... })`; handler type `(event: PrintModeEvent) => void | Promise<void>`; the listener is registered via jobRegistry.subscribeAll from the run loop and fires per emit (job-registry.ts notifyAllSubscribers).

## [MEDIUM] correctness — sdk/src/tools/background-jobs.ts:293 — Log-quota truncation drops the log head without rebasing job.readOffset (or the persisted readOffset), leaving post-truncation reads misaligned
