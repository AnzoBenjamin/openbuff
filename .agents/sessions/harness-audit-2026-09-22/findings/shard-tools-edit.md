## [HIGH] security — packages/agent-runtime/src/tools/handlers/tool/edit-transaction.ts:209 — Capability substitution silently widens a scoped replace_range capability to a whole-file token and can expand the default target range to the entire file
- **Risk:** substituteConfirmedPostEditCapabilities replaces a caller-supplied (possibly scoped) cap.v3 token with the confirmed whole-file post-edit anchor whenever the anchor is fresh (conditions 1-6 gate authenticity, not span equality). Downstream, process-edit-transaction.ts:779 resolves missing target bounds from the SUBSTITUTED token: startLine: (edit.startLine ?? decoded.startLine) + shift. A replace_range edit whose readCapability covered lines 5-10 with omitted startLine/endLine (documented as 'replace the full observed range') therefore becomes a 1..N whole-file overwrite after substitution. The strict gate and authorization grants see the original edits, so no gate catches the widened span.
- **Fix:** Substitute only when the provided token's (startLine, endLine, hash) equal the anchor's, or capture the ORIGINAL decoded token bounds before substitution and use those (edit.startLine ?? originalDecoded.startLine) as the default target range so substitution can never change which lines are replaced. Add a test where a scoped capability with omitted bounds is substituted and assert the replaced span stays within the original capability range.
- **Evidence:** edit-transaction.ts:209 substituteConfirmedPostEditCapabilities maps edits to {...edit, readCapability: confirmed} where confirmed is the whole-file anchor (anchor.startLine === 1 required at line ~232). process-edit-transaction.ts:779: startLine: (edit.startLine ?? decoded.startLine) + shift, endLine likewise at 780, where decoded is the post-substitution whole-file token. resolveReplaceRangeEdit also re-anchors and defaults bounds from decoded.startLine/decoded.endLine.

## [MEDIUM] error-handling — packages/agent-runtime/src/tools/handlers/tool/write-file.ts:603 — Raw internal error.message is interpolated into agent-visible edit error output, contradicting the no-internals policy
- **Risk:** write-file's catch emits `Error: Failed to process the write_file block. ${error.message}` and the application-threw branches in write-file/str-replace/replace-range/edit-transaction interpolate application.error.message directly into errorMessage. tool-executor.ts's MIGRATION NOTE explicitly forbids echoing raw handler internals into agent-visible output (spawn failures use a static string plus a sanitized hint). A thrown internal error (stack-derived message, filesystem paths, provider payloads) is thus leaked into model-visible tool results on the edit path only.
- **Fix:** Return a static safe message plus the tool/path context and log the raw error via logger.warn (matching buildSpawnAgentsHandlerFailureOutput's contract). If a hint is needed, derive it from a narrow allowlisted prefix like extractSanitizedSpawnRecoveryHint does.
- **Evidence:** write-file.ts:603: error: `Error: Failed to process the write_file block. ${typeof error === 'string' ? error : error.message}`. str-replace.ts application.threw branch: `str_replace failed while applying the prepared patch: ${application.error instanceof Error ? application.error.message : String(application.error)}`; replace-range.ts and edit-transaction.ts have the same pattern (`Client threw: ${application.error...}`), while tool-executor.ts documents: 'the raw handler error can carry internal detail that should not be echoed into agent-visible tool output'.

## [MEDIUM] correctness — packages/agent-runtime/src/process-edit-transaction.ts:468 — resolveFailedEdit maps failures back to edit indexes by regex-matching error prose, which model/file content can spoof
- **Risk:** resolveFailedEdit parses /replacement (\d+)/i out of errorMessage to recover the failed replacement index and then maps it through coalescedEdit.replacementEditIndexes. Error messages in this module quote oldString/match excerpts and file paths, so an edit whose content contains the literal text 'replacement 2' can shift the parsed index and misattribute the failure to a different edit/replacement. That corrupts failure.editIndex, failedReplacementIndex, and the recovery object (preferredStrategy/failedEditIndex) the model is told to follow. This is exactly the prose-keyed classification the module's own failureKind comment forbids.
- **Fix:** Thread a structured failedReplacementIndex (and failedEditIndex) out of processStrReplace alongside failureKind and use it directly in resolveFailedEdit; keep the prose regex only as a last-resort fallback or delete it. Add a test where an oldString contains 'replacement 3' and assert the reported editIndex is unaffected.
- **Evidence:** process-edit-transaction.ts:468-493: const replacementMatch = errorMessage.match(/replacement (\d+)/i); const replacementIndex = replacementMatch ? Number.parseInt(...) - 1 : -1; then coalescedEdit.replacementEditIndexes[replacementIndex]. Contrast the comment on classifyTransactionFailureKind: 'so consumers must classify on this field instead of regex-matching errorMessage (which would duplicate the classification and let the copies drift)'.

## [MEDIUM] error-handling — packages/agent-runtime/src/process-edit-transaction.ts:1212 — applyPatch on an untrusted patch edit.diff can throw and escapes the structured transaction failure path
- **Risk:** case 'patch' calls applyPatch(initialContent, edit.diff) with no try/catch. The 'diff' package's applyPatch throws on malformed patch headers instead of returning false, so a malformed or hostile diff aborts processEditTransaction mid-loop with an exception rather than producing a { error, failureKind } entry. The whole edit_transaction call then falls through to tool-executor's generic handler-failure wrapper: failures[]/recovery/errorCode are lost, the atomic 'no files were changed' contract is expressed only as a generic failure, and a multi-file transaction's other targets get no per-path recovery guidance. The patch edit type also ignores requireFreshReadCapability inside processTransactionEdit (unlike str_replace/rewrite_symbol).
- **Fix:** Wrap applyPatch in try/catch returning { error: 'Patch did not apply cleanly to <path>.', failureKind: 'generic' } (and honor requireFreshReadCapability for patch edits the same way str_replace does). Add a malformed-diff test asserting a structured failure entry instead of a thrown error.
- **Evidence:** process-edit-transaction.ts:1208-1215: case 'patch': { ... const content = applyPatch(initialContent, edit.diff); return content === false ? { error: `Patch did not apply cleanly to ${edit.path}.` } : {...} } — no try/catch; processEditTransaction's loop awaits processTransactionEdit without a guard, and handleEditTransaction awaits processEditTransaction with only tool-executor-level catch.

## [MEDIUM] security — packages/agent-runtime/src/util/read-authorization.ts:74 — remintConfirmedPostEditAnchors Path 4 mints authenticated cap.v3 tokens from unauthenticated persisted projectId/runId stamps
- **Risk:** When the stored token does not authenticate (process restart), issuerMatchesCurrent accepts the anchor purely because stored.projectId/runId equal the current ones and then re-issues a fresh HMAC-signed encodeReadCapabilityToken. A tampered durable agent-state entry (or a forged anchor written through any state-persistence bug) with matching stamps and a syntactically valid sha256 contentHash is upgraded into a cryptographically valid read capability, bypassing strict read-before-edit and the context_compacted floor the moment the hash matches current file content. The stamps are not authenticated, so this is a trust boundary weaker than the cap.v3 HMAC it reintroduces.
- **Fix:** Require an additional authenticated binding for the restart path: e.g. sign the persisted anchor record with the same HMAC key at save time (store a signature over path+hash+projectId+runId) and verify it at remint, or drop Path 4 and force a fresh read after restart. Add a tampered-stamp test asserting the anchor is dropped.
- **Evidence:** read-authorization.ts:74-85: const issuerMatchesCurrent = typeof stored.projectId === 'string' && ... && stored.projectId === projectId && stored.runId === runId; // Path 4: process restart — in-process HMAC dies, but stamped issuer matches. if (!tokenAuthenticatesForScope && !issuerMatchesCurrent) continue; result[path] = { ... readCapability: encodeReadCapabilityToken({...}) }. isWellFormedStoredAnchor only checks shape (CONTENT_HASH_PATTERN), not authenticity.

## [MEDIUM] performance — packages/agent-runtime/src/tools/tool-executor.ts:884 — coerceInputScalarsBySchema re-derives z.toJSONSchema(toolParams[toolName].inputSchema) on every tool call

## [MEDIUM] performance — packages/agent-runtime/src/tools/handlers/tool/edit-transaction.ts:428 — Transaction size limits (per-file and rollback-bytes) are enforced only after every snapshot is fully loaded into memory
- **Risk:** mapWithConcurrency (line 428) loads ALL unique-path file contents through requestOptionalFile before the MAX_TRANSACTION_FILE_BYTES / MAX_TRANSACTION_ROLLBACK_BYTES checks run at lines 448-475. The limits exist to bound transaction memory/rollback state, but the allocation (N unique paths x full file bodies, N up to MAX_TRANSACTION_UNIQUE_PATHS) happens first, so a transaction over large files materializes unbounded transient memory before being rejected. The rollback-bytes check also accumulates only after full loads, so no early exit is possible mid-snapshot.
- **Fix:** Stream or size-probe snapshots (e.g. compare content length as each snapshot resolves inside mapWithConcurrency and abort the batch once the running total exceeds the limit), or enforce per-file limits immediately after each load before fetching the next. Add a test asserting a too-large transaction never loads more than the first offending file's siblings up to the limit.
- **Evidence:** edit-transaction.ts:428-446: const snapshots = await mapWithConcurrency(uniquePaths, TRANSACTION_SNAPSHOT_CONCURRENCY, async (path) => { ... await requestOptionalFile(...) }); uniquePaths.forEach((path, index) => initialContentByPath.set(path, snapshots[index]!)); then 448+: let rollbackBytes = 0; for (...) { rollbackBytes += bytes; if (bytes > MAX_TRANSACTION_FILE_BYTES || rollbackBytes > MAX_TRANSACTION_ROLLBACK_BYTES) return {...} }.

## [MEDIUM] api-contract — packages/agent-runtime/src/tools/handlers/tool/str-replace.ts:157 — Edit-tool errorCode vocabularies diverge across modules from the documented closed enum
- **Risk:** process-edit-transaction documents errorCode as a closed enum ('no_match' | 'stale_capability' | 'preflight_failed') with an explicit note that it 'intentionally does not grow', but the handlers emit additional codes on the same error channel: 'str_replace_circuit_breaker' (str-replace.ts:157), 'fresh_read_required' (edit-read-state/str-replace/replace-range), 'occurrence_not_found' (replace-range), and PAYLOAD_TRUNCATED_ERROR_CODE (edit-transaction). ## [LOW] performance — packages/agent-runtime/src/tools/tool-executor.ts:1821 — canonicalScopedToolPath performs blocking realpathSync syscalls per path on the dispatch hot path
- **Risk:** Every filesystem tool call runs canonicalScopedToolPath for each target path, doing realpathSync(projectRoot) plus one realpathSync per missing-ancestor iteration (line 1835) synchronously on the event loop.
