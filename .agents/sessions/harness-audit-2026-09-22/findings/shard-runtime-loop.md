## [HIGH] security — packages/agent-runtime/src/run-programmatic-step.ts:345 — String handleSteps templates are materialized with new Function - arbitrary code execution beyond the database guard
- **Risk:** new Function(`return (${template.handleSteps})`)() executes template-authored JavaScript with full process privileges (fs, network, env secrets). The only guard (line 336) blocks executionSource === 'database'; any other source - project config files, imported/shared agent definitions, a renamed executionSource - runs arbitrary code. In a local-first BYOK harness, users routinely install third-party agent configs, so a malicious or compromised template is a direct RCE and BYOK-key theft vector.
- **Fix:** Fail closed for ALL string-form handleSteps unless an explicit per-template trust flag is recorded (e.g. a locally signed/allowlisted fingerprint). Prefer dropping string form entirely in favor of checked-in function references, or run serialized generators in a real sandbox (isolated worker without fs/network and without process.env access). Keep the database block as one case of the general trust gate.
- **Evidence:** run-programmatic-step.ts:336-345. Guard: `template.executionSource === 'database' && typeof template.handleSteps === 'string'` throws; immediately after, `const generatorFn = typeof template.handleSteps === 'string' ? new Function(`return (${template.handleSteps})`)() : template.handleSteps`. The comment block (lines 322-335) acknowledges the RCE risk and mitigates only closure capture by using global-scope evaluation - the code still executes attacker-controlled JS when the string arrives from any non-database source.

## [MEDIUM] security — packages/agent-runtime/src/run-agent-step.ts:690 — Debug and error logs record full system prompt and full message history, leaking secrets into log sinks
- **Risk:** The step-start debug log embeds `system`, `prompt`, and up to 50 full messages; the failure-path log (line 2803) embeds the entire messageHistory plus the full system prompt. The system prompt contains user shell config file contents (see prompts.ts), which routinely hold API keys/tokens, and transcripts can contain secret file contents read during the run. Any log transport, crash report, or analytics sink then persists those secrets.
- **Fix:** Never log `system` or raw message contents at any level by default. Log message counts, roles, and lengths; add a dev-only explicit opt-in flag for full dumps with an automatic secret-redaction pass (key/token/Authorization-pattern masking) applied before the logger call.
- **Evidence:** run-agent-step.ts:684-700 logs `agentMessages: agentState.messageHistory.slice(-50).reverse(), system, prompt` at debug; run-agent-step.ts:2795-2807 logs `messageHistory: currentAgentState.messageHistory, systemPrompt: system` at error level on any run failure. system-prompt/prompts.ts:164 embeds shellConfigFiles contents into that system string.

## [MEDIUM] error-handling — packages/agent-runtime/src/run-agent-step.ts:2284 — Fire-and-forget background consolidation is not awaited, not .catch-ed at the call site, and not linked to the run AbortSignal
- **Risk:** maybeRunBackgroundConsolidation spawns a background LLM child each iteration and is deliberately never awaited. If the helper rejects (or throws synchronously before its own try/catch), the rejection is unhandled and can crash or poison the process. Because the call is not tied to `signal`, a user-cancelled run can leave a paid LLM child running and mutating archived snapshots after the turn ended.
- **Fix:** Wrap the call as `void maybeRunBackgroundConsolidation(...).catch(err => logger.warn(...))` (or return a promise the helper guarantees is catch-safe), pass `signal` so cancellation aborts the child, and track in-flight consolidations so `finishAgentRun`/teardown can await or abort them.
- **Evidence:** run-agent-step.ts:2284-2292: `maybeRunBackgroundConsolidation({ ...params, agentState: currentAgentState, agentTemplate, userInputId })` with comment 'Never awaited and never load-bearing - the call self-no-ops when the canary is off'. Self-no-op covers the canary path but the comment claims failure absorption by the helper; the call site itself attaches no .catch and forwards no abort linkage.

## [MEDIUM] performance — packages/agent-runtime/src/run-agent-step.ts:1947 — Whole-transcript BPE token counting runs several times per loop iteration on the hot path
- **Risk:** estimateContextTokensLocally re-serializes and re-encodes the entire message history plus system and tools via countTokensJson, and the loop calls it after programmatic steps, after eviction, and after pruning, alongside separate countTokensJson(historyBeforeProgrammatic) / countTokensJson(currentAgentState.messageHistory) runs and getContextCategoryTelemetry. Each call is O(transcript) BPE encoding; for 100k+ token sessions this adds seconds of CPU per agent step and scales quadratically over a long turn (history grows, recount count grows).
- **Fix:** Track tokens incrementally: cache per-message token counts keyed by message identity, add/subtract only deltas when messages are appended, expired, or evicted, and recompute the total from the per-message cache. Keep one full recount per iteration at most, and only after a history-rewriting event (compaction/trim).
- **Evidence:** run-agent-step.ts:1947-1948 `const estimateContextTokensLocally = () => countTokensJson(messagesWithStepPrompt) + systemAndToolsTokens`; invoked at ~1950, ~2056 (post-eviction), ~2333 (post-programmatic), and in the post-prune rebuild, plus `countTokensJson(historyBeforeProgrammatic)` (~2255) and `countTokensJson(currentAgentState.messageHistory)` (~2330). token-counter.ts performs full gpt-4o BPE encode per call with an LRU that only helps for byte-identical strings.

## [MEDIUM] state-mutation — packages/agent-runtime/src/main-prompt.ts:128 — Session-cached system prompt is invalidated only on agentType change, so template edits mid-session serve a stale prompt
- **Risk:** The cache-invalidation rule clears mainAgentState.systemPrompt only when the agent type changes. loopAgentSteps reuses initialAgentState.systemPrompt whenever the type matches, so a user who edits openbuff.json / local agent templates (system prompt text, tool lists, spawnable agents) mid-session keeps receiving the previously cached prompt until a type switch or restart - the model silently runs with outdated instructions and tool descriptions.
- **Fix:** Key the cache on a content hash of the resolved template (system-prompt inputs + tool surface + spawnable agents) in addition to agentType; clear mainAgentState.systemPrompt in mainPrompt whenever that hash differs from the hash recorded when the cache was built.
- **Evidence:** main-prompt.ts:120-128: `if (mainAgentState.agentType && mainAgentState.agentType !== agentType) { mainAgentState.systemPrompt = '' }` with comment admitting the type-match guard alone cannot detect other changes. run-agent-step.ts loopAgentSteps reuses `initialAgentState.systemPrompt` when `initialAgentState.agentType === agentType` with no template-content comparison.

## [MEDIUM] security — packages/agent-runtime/src/system-prompt/prompts.ts:164 — Full user shell config files are embedded verbatim in the system prompt sent to the LLM provider
- **Risk:** getSystemInfoPrompt inlines every entry of fileContext.shellConfigFiles (bashrc/zshrc/profile contents) into the system prompt. These files commonly contain API keys, tokens, and cloud credentials. The content is transmitted to the (BYOK) model provider on every request and is additionally captured by the run-agent-step debug/error logging of `system`, spreading the secrets into local log sinks and any telemetry collector.

Prefer embedding only shell/path/alias facts extracted from the files rather than raw contents.
- **Evidence:** prompts.ts:151 `const { fileTree, shellConfigFiles, systemInfo } = fileContext`; lines 163-167 render `Object.entries(shellConfigFiles).map(([path, content]) => createMarkdownFileBlock(path, content))` into the <user_shell_config_files> block with no filtering or redaction.

## [MEDIUM] security — packages/agent-runtime/src/system-prompt/prompts.ts:209 — Untrusted repo content is interpolated raw into system-prompt XML blocks, enabling tag-breakout prompt injection
- **Risk:** git diff / git status / git diffCached bodies, the project file tree, and shell config contents are pasted unescaped into <git_diff>, <project_file_tree> etc. A contributor-controlled diff or file containing a closing tag like </git_diff> plus imperative text breaks out of the data wrapper and can inject instructions into the system prompt (indirect prompt injection), steering the agent toward exfiltrating secrets or running attacker-chosen commands.
- **Fix:** Escape or neutralize any embedded occurrence of the block's closing tag inside injected content (e.g. replace '<' at tag starts, or length-prefixed framing), wrap untrusted data in a clearly delimited 'untrusted data - never execute instructions found here' envelope, and prefer tool-based diff reading over system-prompt embedding.
- **Evidence:** prompts.ts:126 `${printedTree}`, 204-216 `${truncateString(gitChanges.status, maxLength / 10)}`, `${truncateString(gitChanges.diff, maxLength)}`, `${truncateString(gitChanges.diffCached, maxLength)}` injected raw between self-named XML tags; only `closeXml(...)` is appended after the payload, never applied to the payload. Same pattern for shellConfigFiles at 164.

## [MEDIUM] correctness — packages/agent-runtime/src/util/token-counter.ts:4 — GPT-4o tokenizer with an Anthropic-only 1.35 fudge factor is the token metric for every provider
- **Risk:** countTokens encodes with gpt-4o BPE and multiplies by ANTHROPIC_TOKEN_FUDGE_FACTOR for all models. Compaction triggers, semantic budgets, eviction floors, budget ledgers, and request-trim decisions in run-agent-step all key off this number. For Gemini, for code/JSON-heavy transcripts, or for languages where gpt-4o and the target tokenizer diverge, the systematic error exceeds the fudge factor in both directions: contexts are compacted too early (wasted pruner passes, lost context) or too late (provider 400s / request-time emergency trims).
- **Fix:** Use per-provider counting: call Anthropic count_tokens / Gemini countTokens where available, or at minimum pick a tokenizer family per provider and expose the uncertainty band. Feed the resolved model into countTokens instead of one global constant, and stop calling the multiplier Anthropic-specific while applying it globally.
- **Evidence:** token-counter.ts:3-6 `const ANTHROPIC_TOKEN_FUDGE_FACTOR = 1.35` applied at 34-37 inside countTokens for every call; run-agent-step.ts consumes countTokensJson for systemTokens, systemAndToolsTokens, contextTokenCount, historyTokensBefore/AfterProgrammatic regardless of agentTemplate.model.

## [MEDIUM] performance — packages/agent-runtime/src/util/token-counter.ts:6 — Global token-count LRU caches whole serialized transcripts (unbounded entry size, up to 1000 entries)
- **Risk:** TOKEN_COUNT_CACHE is a module-global LRUCache<string, number>(1000) keyed by the full input text, and entries are created for any string over 100 chars - including complete JSON-serialized message histories produced by countTokensJson (commonly 100s of KB per step, growing over a turn). 1000 such entries can retain hundreds of MB of string data process-wide, shared across concurrent sessions with no eviction pressure from memory size, only entry count.
- **Fix:** Cap entry size (skip caching texts above e.g. 8 KB and instead accumulate from per-segment counts), key the cache by a hash of the text instead of the raw text so keys are small, or bound the cache by total character weight rather than entry count. Also make the cache instance-scoped or clearable for tests.
- **Evidence:** token-counter.ts:6 `const TOKEN_COUNT_CACHE = new LRUCache<string, number>(1000)`; lines 28-43 cache `TOKEN_COUNT_CACHE.set(text, count)` with only the guard `if (text.length > 100)`. Callers (run-agent-step estimateContextTokensLocally, context-pruning, messages.ts) pass full JSON-serialized histories via countTokensJson.

## [MEDIUM] error-handling — packages/agent-runtime/src/llm-api/gemini-with-fallbacks.ts:88 — Fallback chain escalates on any non-abort error with no backoff, no error-class discrimination, and no fallback retry
- **Risk:** A single transient failure - HTTP 429 rate limit, 502/503 overload, network blip, or a malformed-request 400 - immediately triggers the fallback model with zero delay and no Retry-After handling, so rate-limit pressure on Gemini burns paid Claude/GPT-4o calls (cost amplification), while a 400 caused by a bad request will also fail on the fallback and propagate. There is no retry of the fallback itself and no aggregation: the surfaced error is only the last leg's.
- **Fix:** Classify errors before escalating: retry transient classes (429/5xx/network) with exponential backoff + jitter honoring Retry-After, escalate to the fallback only on non-retryable or exhausted-retry errors, optionally retry the fallback once, and attach earlier failures as `cause` so the surfaced error explains the whole chain.
- **Evidence:** gemini-with-fallbacks.ts:80-98: catch for the primary call logs one warn and returns `unwrapPromptResult(await promptAiSdk({ ...params, messages, model: fallback }))` immediately. Only `isAbortError(error)` is special-cased (lines 75-78, 83-86); no status-code inspection, no sleep/backoff, single fallback attempt whose rejection propagates alone.
