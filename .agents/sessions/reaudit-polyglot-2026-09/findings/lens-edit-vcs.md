## [HIGH] state-mutation — sdk/src/services/workspace-mutation-broker.ts — EV-1 Per-agent copy-on-write workspaces (best-of-N) are impossible: one shared working tree behind one global lock
- **Risk:** Current state: every mutation from every agent/sub-agent targets the single workspaceRoot and serializes through one mkdir lock (acquireWorkspaceLock, 20ms poll, 10s timeout). Nothing in sdk/, agent-runtime/, or cli/src creates git worktrees (code_search for worktree/libgit2/jj returned only comments and deny-rules in terminal-command-policy.ts). Parallel sub-agents therefore race on the same files, and a stale_state from one agent forces rereads in the others. Best-of-N implementations cannot run side by side. Candidate: Rust gitoxide (gix) or git2 in-process worktrees + an in-memory index/tree builder, with reflink/clonefile COW checkouts (reflink-copy crate) for untracked/ignored build state. Feature unlocked: every sub-agent gets its own isolated tree (lane), built from HEAD+dirty state without stashing. processEditTransaction already computes full post-edit content in memory, so edits can be written as blobs/trees to a lane ref without touching disk and materialized only for validation. User-visible value: 'try 3 approaches in parallel, run tests in each, keep the winner'; sub-agents stop clobbering each other; the user's own working tree stays untouched until they accept. Cost/risk: medium-high. Broker receipts, the cap.v3 scope (projectId is the projectRoot, so it must gain a lane id), and FileMutationResultV1 must become lane-aware. Can TS do it? Partly: spawning `git worktree add` works but makes full on-disk copies, has no virtual index, and spawns a process per operation. In-memory tree construction and COW are practical only natively.
- **Fix:** Add a Workspace Lane abstraction (laneId in the broker identity, the cap.v3 scope, and the journal). Back it with a gix/git2 napi module or a small Rust sidecar that exposes createLane(baseRef), writeTree(lane, files), materialize(lane, dir, reflink), and diffLanes(). Keep the default lane equal to today's single-tree behavior.
- **Evidence:** workspace-mutation-broker.ts: class doc says it is a 'Cooperative local compare-and-swap authority ... does not provide kernel-enforced exclusion'. acquireWorkspaceLock uses fs.mkdir(this.lockPath) with a sleep(this.lockPollMs) loop. brokerDir is keyed only by repositoryId/workspaceId. rewrite-symbol.ts: capabilityScope projectId = fileContext.projectRoot, with no lane dimension. No worktree creation code anywhere in sdk/src, cli/src, or agent-runtime/src.

## [HIGH] state-mutation — cli/src/utils/run-state-storage.ts:321 — EV-2 Undoable agent turns: checkpoints capture agent state but not file state, and receipts store hashes, not bytes
- **Risk:** Current state: turn-checkpoint.json stores only a serialized mainAgentState snapshot (getCheckpointPath, 'taken every ~30s'). Broker receipts and the workspace journal record beforeHash/afterHash/snapshotId, never content (WorkspaceMutationReceipt has no blob ref; WorkspaceJournalService.advance stores only WorkspaceStateV1). changeFiles holds rollback bytes only in memory for the length of one transaction (MAX_TRANSACTION_ROLLBACK_BYTES). So no turn can be undone after it completes, and file changes made by run_terminal_command (codegen, formatters, `sed`) bypass the broker completely. Candidate: Rust jj-lib (Jujutsu) operation-log model. Each turn boundary snapshots the whole working copy as a commit, and the op log records every workspace state, so `op undo`/`op restore` is O(1) and covers ALL changes, including shell-command side effects, with no stash. Feature unlocked: /undo and /redo per turn or per sub-agent, 'restore to before turn 7', and undo that also reverts what basher did. User-visible value: fearless autonomy, the main trust feature of agent CLIs (similar to Claude Code checkpoints, but covering shell effects too). Cost/risk: medium. Embed jj-lib via napi, or colocate a .jj repo and drive the jj CLI as a sidecar. Colocated jj rewrites git refs, which is risky in users' repos, so a private op store under stateDir is safer. Can TS do it? Mostly, via git plumbing (GIT_INDEX_FILE temp index + write-tree + commit-tree to a private ref per turn). That route has no op-log semantics, concurrent-op merge, or conflict-as-data model, which jj provides for free.
- **Fix:** At each turn boundary (where the checkpoint is saved), snapshot the working tree to a private content-addressed ref: phase 1 via TS git plumbing, phase 2 via jj-lib. Link snapshot ids into WorkspaceStateV1 and the broker receipts as an additive schema field. Expose /undo-turn and /restore <turn>.
- **Evidence:** run-state-storage.ts:316-323 checkpoint doc: 'serialized mainAgentState snapshot taken every ~30s'. workspace-mutation-broker.ts WorkspaceMutationReceipt fields: expectedHash/beforeHash/afterHash/stagingPath, no content. workspace-journal.ts advance() persists only state/snapshotId. change-file.ts changeFiles: rollback uses in-memory beforeContent that is discarded after return.

## [HIGH] correctness — packages/agent-runtime/src/process-structured-edit.ts — EV-3 Structured/AST edits are regex-per-language, and rewrite_symbol degrades to text replace: no format-preserving codemods
- **Risk:** Current state: the 'structured' edit kinds are only insert_text, insert_import, and remove_import, implemented with 50+ hand-written per-language regexes (JS_IMPORT_REGEX, GO_IMPORT_BLOCK_REGEX, PHP_TRIVIA_REGEX, ...). Multi-line imports, comments, and string literals can confuse them. rewrite_symbol resolves a span with tree-sitter and then delegates to handleStrReplace with the old text as oldString, so it is a textual splice, not an AST operation. process-str-replace.ts:1728 isResultDelimiterBalanced counts brackets character by character, including inside strings and comments. :1775 getTranspiledTopLevelSymbolName uses Bun.Transpiler, so it works for JS/TS only. Candidate: Rust ast-grep (tree-sitter pattern match plus rewrite templates across ~25 languages). Precise per-language options exist too: libCST (Python, lossless CST), dave/dst (Go, decoration-preserving), ts-morph/recast (TS, already TS-native). Feature unlocked: new edit kinds such as rename_symbol (scope-aware, cross-file with the indexer), structural_replace (pattern -> template with metavariables), add/remove parameter, wrap-in-try, and move-symbol-to-file. Also syntax-aware preflight for every language instead of Bun-transpiler-only. User-visible value: large refactors in one deterministic call with fewer tokens and no oldString copy failures, which are the dominant recovery path documented in deterministic-edit-system.md. Cost/risk: low-medium. @ast-grep/napi already ships prebuilt napi binaries. Output must still flow through processEditTransaction as full content so the ledger, cap.v3, and broker contracts are unchanged. Can TS do it? For JS/TS, yes (ts-morph/recast). For multi-language, format-preserving structural rewrite, not realistically: the ecosystem is Rust (ast-grep), Python (libCST), and Go (dst).
- **Fix:** Add an 'ast_rewrite' StructuredEditOperation that calls ast-grep (napi) to produce new full content, then passes it through the existing transformation ledger/preflight. Replace isResultDelimiterBalanced and the Bun-only symbol identity with a tree-sitter ERROR-node check for every language.
- **Evidence:** process-structured-edit.ts: StructuredEditOperation = insert_text | insert_import | remove_import. buildImportLineRegex has per-extension regex branches. rewrite-symbol.ts: 'applies the change through the existing str_replace machinery ... using the symbol's current text as a precise oldString'. process-str-replace.ts:1728-1754 bracketDelta loop has no string/comment awareness. :1761-1782 declares Bun.Transpiler, 'only available in the Bun runtime'.

## [HIGH] correctness — packages/agent-runtime/src/process-edit-transaction.ts — EV-4 Parallel/overlapping edits are rejected instead of merged: no syntax-aware 3-way merge
- **Risk:** Current state: within a transaction, the transformation ledger (appendTransformationLedgerEntries via diffChars) fails closed when a replace_range overlaps any byte changed earlier ('overlap bytes changed earlier in this transaction'), or when provenance is unmappable. Across agents, the broker's CAS rejects any concurrent change (stale_state), which forces a full reread and rebuild. 'patch' edits use jsdiff applyPatch with no fuzz or 3-way fallback ('Patch did not apply cleanly'). So two sub-agents editing different functions in the same file conflict at file granularity, and landing parallel work always needs human or model re-edits. Candidate: Rust mergiraf (tree-sitter syntax-aware 3-way merge, usable as a git merge driver) plus gix/git2 in-memory merge_trees. Feature unlocked: auto-merge of sub-agent lanes (EV-1) when their edits touch disjoint AST nodes even on the same lines (e.g. both add imports, both add a match arm). Stale-state recovery becomes 'rebase my edit onto the new base' instead of 'reread and rebuild the whole transaction'. User-visible value: true parallel multi-agent editing, far fewer abort/retry loops, and conflicts only when they are semantic. Cost/risk: medium. mergiraf is a CLI/lib (GPL-3.0 license: check compatibility before embedding; a sidecar process may be needed). Merge output must re-enter preflight syntax validation. Can TS do it? A line-based diff3 merge is easy in TS (node-diff3). Syntax-aware merge is not: no maintained TS equivalent exists.
- **Fix:** On broker stale_state for a path whose base content is known (the transaction snapshot), attempt base/ours/theirs merge: diff3 first, then mergiraf. Commit only if the result parses and matches expectations, and report 'merged' in the receipt. Use the same machinery to land EV-1 lanes.
- **Evidence:** process-edit-transaction.ts getEffectiveReplaceRangeEdit: 'original lines ... overlap bytes changed earlier in this transaction, so exact provenance is unavailable'. appendTransformationLedgerEntries errors with 'a changed interval originated in text introduced by a prior edit'. The patch case: applyPatch(...) then 'Patch did not apply cleanly'. change-file.ts prepareTransactionChange returns 'stale_state' on hash mismatch, with no merge attempt.

## [MEDIUM] state-mutation — sdk/src/tools/change-file.ts — EV-5 Multi-file transactions are sequential commit plus best-effort rollback, not crash-atomic
- **Risk:** Current state: changeFiles commits prepared changes one by one (commitPreparedTransactionChange in a loop) and on error rolls back in reverse using in-memory bytes. If the process is killed mid-loop, some files are left applied. The broker recovers per receipt (per file), not per transaction, and receipts carry no transaction grouping. The 'rollback_incomplete' status exists precisely because atomicity is not guaranteed. Candidate: Rust, either (a) a VCS-backed commit, where a gix tree write plus a single ref update gives an atomic transaction identity and the working-copy checkout becomes the replayable step, or (b) a redb/SQLite WAL intent log with transaction-level redo/undo, plus renameat2(RENAME_EXCHANGE)/ReplaceFileW via the nix/windows crates. Feature unlocked: all-or-nothing multi-file edits that survive a crash or SIGKILL. A 'transaction id' becomes a first-class undo unit. Value: no half-applied refactors after a crash. Cost/risk: medium, and the broker receipt schema must be versioned (additive transactionId). Can TS do it? A transaction-level intent log is doable in TS (bun:sqlite). renameat2 exchange and kernel-level atomic swaps are not reachable from Bun/Node.
- **Fix:** Add a transactionId to broker receipts and a durable transaction intent record, written before the first file commit, that lists every staged path plus the before/after blob. Recovery then replays or undoes the whole group. Optionally store the blobs in the EV-2 content store so rollback bytes are durable instead of in-memory.
- **Evidence:** change-file.ts changeFiles: `for (const change of prepared) { committed.push(change); await commitPreparedTransactionChange(...) }`, then catch -> rollbackPreparedTransactionChange in reverse, with status 'rollback_incomplete' | 'rolled_back'. workspace-mutation-broker.ts: recoverPendingReceipts iterates per-file receipts with no grouping field.

## [MEDIUM] performance — sdk/src/tools/git-status.ts:30 — EV-6 Git is shell-out only: no blame/log context, hunk staging, or in-memory index for agents
- **Risk:** Current state: runGit spawns `git` per call. getChangeReviewBundle runs 4-5 git processes (status, rev-parse, status -uall, diff --binary HEAD, optionally HEAD~1 diff) and then readFileSync on every changed file. cli/src/utils/git.ts getDiffStats uses execSync with a 5s timeout on the UI thread. git_branch only does checkout -b/branch and refuses a dirty tree. The agent toolset has no blame, log-for-lines, per-hunk stage, or in-memory merge tool. The feature cost, beyond speed: agents cannot ask 'why/when was this line written'. Candidate: Rust gix (gitoxide) in-process, which provides blame, rev-walk, diff with rename detection, index manipulation, and status with an untracked cache. Feature unlocked: a blame_context tool (last-touching commit message and PR per symbol span, fed into read_files editAnchor metadata), stage_hunks/commit tools with exact hunk selection, live git status in the TUI without blocking, and review bundles computed from tree diffs (no HEAD~1 heuristic). Value: better edits from historical intent, and clean agent-authored commits split by concern. Cost/risk: medium. gix blame is newer and less complete than git's, so keep the CLI as fallback. Can TS do it? Via the CLI, yes (git blame --porcelain), at a per-call spawn cost. isomorphic-git lacks blame performance and worktrees. The language move here is mostly about latency and a structured API, so this is medium, not high.
- **Fix:** Add blame_context and stage_hunks tools. Implement them first over the git CLI with porcelain parsing, then swap in a gix napi backend behind the same interface. Move getDiffStats off execSync.
- **Evidence:** git-status.ts:30 `spawn('git', args, ...)`. get-change-review-bundle.ts buildSnapshotId: runGit diff --binary HEAD, plus fs.readFileSync per file. The HEAD~1 fallback reviews only the last commit. cli/src/utils/git.ts:38 execSync('git status --short --porcelain', {timeout: 5000}). git-branch.ts: dirty-tree refusal, then `checkout -b`.

## [MEDIUM] correctness — sdk/src/tools/get-change-review-bundle.ts — EV-7 Review bundles are line diffs: structural diff would cut reviewer noise and tokens
- **Risk:** Current state: reviewers and the security-reviewer consume `git diff --no-color` text truncated at max_chars (80k). Reformatting, moved blocks, or reindentation inflate the diff and hide semantic changes, and truncation hides the tail. This is separate from the prior audit's imara-diff word diffs, which covered TUI rendering. This finding is about what the model reviews. Candidate: Rust difftastic (tree-sitter structural diff; library use is unofficial, so run it as a CLI sidecar with --display json) or a gumtree-style AST diff built on ast-grep/tree-sitter. Feature unlocked: a 'semantic_diff' view in the review bundle (changed nodes per symbol, with move/reformat-only changes collapsed), plus per-symbol change summaries mapped to the code-map. Value: cheaper, more accurate automated review; fewer false findings from formatting churn; larger changes fit in the reviewer context. Cost/risk: low-medium, additive field. Can TS do it? Not with quality: no maintained TS structural differ exists.
- **Fix:** Add an optional structuredDiff field to get_change_review_bundle, generated by a difftastic sidecar (JSON output) and limited to supported languages, with fallback to the line diff. Keep the snapshotId computation unchanged.
- **Evidence:** get-change-review-bundle.ts: gitStatus({include_diff: true, max_chars: params.max_chars ?? 80_000}); diff = value.diff; the committed fallback runs `git diff --no-color HEAD~1 HEAD`.

## [MEDIUM] state-mutation — sdk/src/services/workspace-journal.ts — EV-8 Time-travel session replay needs a content store: the journal is hashes-only
- **Risk:** Current state: WorkspaceJournalService persists a single 'workspace' record with the current state/snapshotId and a revision counter. Previous states are overwritten, not appended, and actions carry no bytes. You cannot replay a session, bisect which turn broke tests, or diff turn N against turn M. Candidate: a Rust content-addressed store (gix ODB or jj op log, from EV-2), optionally with zstd-dictionary compression (zstd crate) for cheap per-turn snapshots. Feature unlocked: session time travel (scrub through turns, see the tree at each turn), automated 'bisect by turn' against a test command, and deterministic replay of tool calls against a historic tree for evals. Value: debuggability of long autonomous runs, and eval reproducibility. Cost/risk: medium (storage growth needs GC and a retention policy). Can TS do it? Yes, via git plumbing (hash-object/write-tree to a private ref). Native makes per-turn snapshots of large repos cheap enough to run on every tool call rather than every turn.
- **Fix:** Make the journal append-only, with each revision referencing a tree id in the private snapshot ref from EV-2. Add a /timeline view and a bisect-turns command that runs a user test command against materialized lanes (EV-1).
- **Evidence:** workspace-journal.ts advance(): store.put('workspace-journals', {id: 'workspace', revision: existing.revision+1, snapshotId, state}, existing?.revision), a single overwritten record with no content or tree references.

## [LOW] error-handling — packages/agent-runtime/src/tools/handlers/tool/edit-application-coordinator.ts — EV-9 Concurrent human+agent editing: CRDT is feasible, but TS already has it (Yjs); no language move needed
- **Risk:** Current state: a human editing a file in their editor while the agent works causes stale_state/stale_snapshot, and invalidatePreparedEditPaths revokes read authorization, which forces a reread and a rebuilt edit. Candidate: automerge/yrs (Rust) is one option. However, Yjs is TS-native and is the reference implementation, so a language move is NOT justified for this feature. The real prerequisite is an editor bridge (LSP/extension) that streams human keystrokes as ops. Feature unlocked: agent edits rebase onto live human edits character-wise; shared cursors/presence in the IDE. Value: pairing without 'file changed, rereading' loops. Cost/risk: high product cost (needs an editor plugin), low language cost. Can TS do it? Yes.
- **Fix:** Treat this as an editor-integration feature built on Yjs in TS. In the meantime, the diff3/mergiraf rebase from EV-4 covers the file-save granularity case without CRDTs.
- **Evidence:** edit-application-coordinator.ts collectStaleSnapshotPaths revokes on stale_snapshot|stale_state, then invalidatePreparedEditPaths(reason 'stale_snapshot'). deterministic-edit-system.md: an external modification 'fails closed and requires a fresh read'.

## [LOW] api-contract — sdk/src/tools/git-branch.ts — EV-10 Landing agent work: refuse-if-dirty branching instead of in-memory rebase/merge
- **Risk:** Current state: git_branch refuses a dirty tree ('Commit or stash changes before branching') and only supports create/switch, with no rebase/merge/cherry-pick tool. Moving agent work onto a branch, or rebasing onto an updated main, is left to raw shell commands, which the terminal-command policy restricts. Candidate: gix/git2 in-memory rebase and merge_trees, or `git merge-tree --write-tree` (git >= 2.38, CLI). Feature unlocked: 'land lane X on branch Y' without touching the user's working tree; conflict reports as structured data. Value: safe PR creation from sub-agent lanes. Cost/risk: low-medium. Can TS do it? Mostly, via modern git CLI plumbing. Native only matters when combined with the EV-1 lanes.
- **Fix:** Add a land_lane tool: merge-tree --write-tree (TS) now, gix later. Return conflicts as a structured list and never rewrite the user's checkout.
- **Evidence:** git-branch.ts: the allowDirty=false default returns 'Working tree is dirty. Commit or stash changes before branching.' Branch args are only ['checkout','-b',name] or ['branch',name].
