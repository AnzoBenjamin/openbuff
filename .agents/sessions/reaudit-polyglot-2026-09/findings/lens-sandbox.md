## [CRITICAL] security — sdk/src/tools/terminal-command-policy.ts:2092 — SB-1 The whole execution boundary is a 2452-line lexical bash parser; replace with kernel sandbox (Landlock+seccomp / Seatbelt / AppContainer) via a native exec shim
- **Risk:** Current state: every profile (read-only, workspace-write, tmux-test, git-commit...) is enforced by regex + a hand-written quote scanner over the command STRING (evaluateTerminalCommandPolicy :2092, TMUX_UNSAFE_EXECUTABLES :855, findOutsideAbsolutePath :1928, env-dump wrapper list :195). The string is then handed to `bash -c` (run-terminal-command.ts:508). Anything the shell does after that is unconstrained: workspace-write allows `node build.js`/`python3 x.py`/`make`, and that program can read ~/.ssh, write outside the project, or exfiltrate. Read-only 'network mutation' is a regex on curl/wget flags (:1502). The policy can only ever be a UX lint, never a boundary. The prior report mentioned 'OS-level sandboxing' as a one-liner; it did not identify that the existing profile system is the thing to be re-grounded, nor the exec-shim architecture.
- **Fix:** Candidate: Rust exec shim (~1-2k LoC) spawned by TS in place of `bash`: `openbuff-sandbox --profile workspace-write --rw <root> --ro / -- bash -c ...`. Crates: `landlock` (FS allowlist, Linux 5.13+, ABI v4 adds TCP bind/connect rules), `seccompiler` or `libseccomp` (syscall filter: ptrace, mount, keyctl, bpf), `nix` for unshare(CLONE_NEWUSER|NEWNS|NEWNET). macOS: generate an SBPL profile and exec via sandbox_init/`sandbox-exec` (C/Swift or Rust `libc` FFI). Windows: AppContainer + restricted token + Job Object (`windows` crate). Precedent: codex-rs `linux-sandbox`/`seatbelt` modules. Each TerminalPermissionProfile compiles to a capability set (fs rw roots, ro roots, net on/off, allowed hosts). Keep the lexical policy as a fast pre-check that yields good error messages. Feature unlocked: profiles become ENFORCED guarantees (read-only really cannot write; workspace-write really cannot touch $HOME), which in turn lets you RELAX the lexical policy and stop false-denying legitimate commands (`bash -c`, `find -exec`, `sed -i` in tmux-test). User value: fewer 'Command denied' walls + actual safety on untrusted repos. Cost: medium; Landlock unavailable on old kernels/WSL1 -> must degrade loudly to 'policy-only' tier and report tier in tool output (like FilesystemCapabilitySnapshot tiers). Could TS do it? No for Linux: Landlock/seccomp must be applied in the child between fork and exec; Node/Bun spawn exposes no pre-exec hook. macOS `sandbox-exec` is invocable from TS as a wrapper (deprecated but works) — so macOS-only could be TS; Linux/Windows need a native helper binary. Bubblewrap (`bwrap`) is a C alternative TS could shell out to, at the cost of a system dependency.
- **Evidence:** terminal-command-policy.ts:2092 evaluateTerminalCommandPolicy operates purely on `params.command` string; :855 executable denylist; :1502 regex-based network rule; run-terminal-command.ts:508 `spawn(shell, [...shellArgs, command], { cwd, env: processEnv, stdio: 'pipe', detached: !isWindows })` — no privilege reduction of any kind.

## [HIGH] security — sdk/src/env.ts:49 — SB-2 Every child inherits the full process.env incl. BYOK/OAuth keys; add secret broker + egress proxy (credential injection at the network edge)
- **Risk:** getSystemProcessEnv() returns `process.env` verbatim (env.ts:49-51), merged into every SYNC and BACKGROUND child (run-terminal-command.ts:413, :485). The same process reads OPENBUFF_API_KEY, BYOK OpenRouter key and ChatGPT OAuth token from env (env.ts:41-65). The policy spends hundreds of lines denying `printenv`/`env`/`export -p` (terminal-command-policy.ts:195-430) but any allowed interpreter (`node -e` is blocked only in read-only; `node script.js`, `bun test`, a postinstall script) reads process.env directly. Secret exposure to arbitrary repo code is the default.
- **Fix:** Two layers. (a) TS, trivially: build a child env from an allowlist and strip known credential vars — do this now, no language change needed (honest). (b) Native feature: a secret broker + egress proxy. Children get placeholder tokens (e.g. OPENBUFF_SECRET_ref_123); a local MITM/CONNECT proxy (Rust `hyper`+`rustls`+`rcgen`, or Go `net/http` + `goproxy`) substitutes real values only for allowlisted destinations (api.github.com gets GH token, registry.npmjs.org gets npm token). Enforcement requires the network namespace from SB-1/SB-3 so the child cannot bypass the proxy. Feature unlocked: agents can run `gh`, `npm publish --dry-run`, cloud CLIs without ever holding a raw secret; secrets cannot be exfiltrated to an arbitrary host even by a malicious test. Cost: medium-high (CA trust injection per toolchain: NODE_EXTRA_CA_CERTS, SSL_CERT_FILE, REQUESTS_CA_BUNDLE). TS could run the proxy (Bun HTTP server can do CONNECT) but cannot force children through it without the kernel netns — the enforcement half is native.
- **Evidence:** env.ts:49 `export const getSystemProcessEnv = (): NodeJS.ProcessEnv => { return process.env }`; run-terminal-command.ts:413/:485 `{ ...getSystemProcessEnv(), ...(env ?? {}) }`; terminal-command-policy.ts:36-37 WORKSPACE_ENV_DUMP_REASON — the protection is only against literal dump commands.

## [HIGH] state-mutation — sdk/src/tools/run-terminal-command.ts:478 — SB-3 Shell commands have no rollback and imprecise attribution; copy-on-write overlay workspaces give exact write-sets, instant undo and speculative execution
- **Risk:** FilesystemAuthority gives edit tools CAS commits and receipts (filesystem-authority.ts: beginCommit/finishCommit/issueCommittedReceipt), but run_terminal_command bypasses it entirely. Its only mutation accounting is `git status --porcelain -uall` before/after (listDirtyPaths, :432/:478, dirtyDelta). That misses: gitignored outputs (dist/, node_modules, .env written by a script), files that were already dirty and got modified again, anything outside the repo, and reverts. There is no undo for a bad `rm`, codemod, or `git checkout`.
- **Fix:** Candidate: Rust (or Go) workspace-overlay component. Linux: unprivileged overlayfs in a user+mount namespace (kernel 5.11+) or `fuse-overlayfs`; lowerdir = project, upperdir = per-command scratch. btrfs/XFS: reflink snapshot (`ioctl FICLONE`). macOS: APFS `clonefile(2)` of the tree. Windows: ProjFS or plain copy fallback. After the command, the upperdir IS the exact write set (incl. whiteouts = deletions); commit = merge through FilesystemAuthority CAS (produce CommitReceiptV1 for shell writes too), discard = rm upperdir. Feature unlocked: (1) `/undo` for any shell command, (2) touchedPaths becomes exact including ignored files and deletions, (3) speculative execution — run N candidate fixes/test runs in parallel isolated overlays and promote the winner. Cost: medium-high; overlay semantics differ per OS; build caches inside overlay must be tuned (bind node_modules read-only). Could TS do it? Partially: `cp -c`/`cp --reflink=auto` and `git worktree` are shell-outs TS can drive for coarse snapshots; mounting overlayfs inside a namespace for a single child requires the native pre-exec shim from SB-1.
- **Evidence:** run-terminal-command.ts:176-203 listDirtyPaths parses porcelain output; :478-700 SYNC path computes `dirtyDelta(dirtyBefore, dirtyAfter)` (only NEW dirty paths; `if (!before.has(path))`), so re-modification of an already-dirty file is invisible. filesystem-authority.ts:628 comment concedes external check/write races are not closed without native authority.

## [HIGH] correctness — sdk/src/tools/background-jobs.ts:55 — SB-4 Process-tree control is pgid signals + 250ms log polling; cgroups v2 / pidfd / Job Objects give guaranteed kill, resource limits and real exit codes
- **Risk:** terminateProcessTree sends a signal to -pid (:55-75); any descendant that calls setsid/double-forks (daemons, `nohup`, docker, dev servers spawning workers) escapes and survives kill_job. There is no memory/CPU/pids cap: a fork bomb or a 30GB test run takes down the host. Log quota is enforced by a setInterval that stats the file every 250ms (:782, MAX_BACKGROUND_LOG_BYTES :177) so a fast writer overshoots. Pid-reuse protection relies on Linux-only /proc starttime (:1144) and on HMAC'd metadata that is still a TODO (SEC-5, :1291); on macOS/Windows recovered jobs are refused kill. Recovered jobs can only settle as 'lost' because the CLI is not the parent (recheckRecoveredJobLiveness).
- **Fix:** Candidate: Rust supervisor using cgroups v2 (`cgroups-rs` or direct cgroupfs writes under a systemd user delegation), `pidfd_open`/`pidfd_send_signal` (race-free, no pid reuse), PR_SET_CHILD_SUBREAPER so orphans reparent to the supervisor; macOS kqueue EVFILT_PROC + posix_spawn process groups; Windows Job Objects with JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE and memory limits (`windows` crate). Go is an equally good fit (os/exec + golang.org/x/sys/unix, containerd/cgroups). Feature unlocked: kill_job kills the entire tree always; per-job memory.max/cpu.max/pids.max; live per-job CPU/RSS/IO numbers for the TUI job cards; OOM surfaced as a structured 'resource_exceeded' status instead of a mystery exit 137. Cost: medium; cgroup delegation absent on some distros/containers -> tiered fallback. TS alternative (honest): `systemd-run --user --scope -p MemoryMax=...` wrapper gives most of the Linux value with zero native code, if systemd is present; pidfd and Job Objects are not reachable from Bun.
- **Evidence:** background-jobs.ts:62 `process.kill(-child.pid, signal)`; :719 `stdio: ['ignore', outFd, outFd], detached: os.platform() !== 'win32'`; :782 `setInterval(() => {... fs.statSync(logFile).size ...}, 250)`; :1144 readProcessStartTime returns undefined off-Linux; :1291 'SEC-5 HMAC metadata authenticity is a follow-up'.

## [HIGH] correctness — agents/tmux-cli.ts:485 — SB-5 tmux helper is an executable bash script in world-writable /tmp that other defenses must special-case; teardown command ends in a dangling `'>` (likely syntax error, teardown never runs)
- **Risk:** New angle beyond prior #12 (PTY sidecar): the helper is written to /tmp/tmux-helper-<uuid>.sh and chmod +x'd (:485-520), then executed by every later step. filesystem-authority.ts:66-86 explicitly documents that OWNED_TEMP_REFUSED_EXTENSIONS exists largely because of this script ('the ONLY defense against a file-changing tool staging a script'), and findOutsideAbsolutePath exempts all /tmp tokens — the security model has a hole shaped exactly like this helper. Separately, the finally-block teardown builds `helperPath + " stop '" + sessionName + "' >/dev/null 2>&1; rm -f '" + helperPath + "'>"` — the trailing `>` with no target is a bash parse error, so neither `stop` nor `rm` executes and sessions/helpers leak (and under tmux-test policy hasUnsafeTmuxWriteRedirection would deny it anyway since target != /dev/null). Also: capture-pane polling every 0.25s (:359, :435), idle = 'string unchanged', which cannot distinguish 'waiting for input' from 'thinking'. Not verified: whether handleSteps tool calls are policy-evaluated under 'tmux-test' (setup uses `cat >`, `find -exec rm`, `chmod`, all denied by that profile).
- **Fix:** Immediate TS fix: remove the stray `>`; add a test that executes the teardown string with `bash -n`. Language move: a native PTY host (Rust `portable-pty` + `vt100` or `alacritty_terminal` for a full VT state machine; Go `creack/pty` + `vt10x`) exposed as a first-class `terminal_session` tool — no tmux dependency, no /tmp executable, no helper shipped in a prompt. Feature unlocked: semantic screen assertions (cursor position, cell attributes, alt-screen state), true idle detection via PTY read quiescence + foreground-process-group state (tcgetpgrp shows whether the shell or the app is waiting on input), exact resize testing, asciinema-format recordings for the parent instead of text captures. Removes the reason for the OWNED_TEMP executable-extension carve-out. Cost: medium; must preserve agent outputSchema. TS: node-pty exists but is a native addon with poor Bun support; xterm-headless (TS) is a viable vt parser — the PTY allocation is the native part.
- **Evidence:** tmux-cli.ts:485 `const helperPath = '/tmp/tmux-helper-' + sessionName + '.sh'`; :502 `find /tmp -maxdepth 1 -type d -name 'tmux-captures-*' -mmin +1440 -exec rm -rf {} +`; teardown near :760-770 ends with `"'>"`; filesystem-authority.ts:66-86 comment on tmux-helper-<session>.sh; terminal-command-policy.ts:1236 hasUnsafeTmuxFileMutation and :855 list find/chmod/tee as tmux-test-unsafe.

## [HIGH] security — sdk/src/tools/run-terminal-command.ts:340 — SB-6 Approval of a high-impact action re-runs the command with mode:'user', which disables ALL profile policy — approval should widen a sandbox capability, not remove the boundary
- **Risk:** After authorizeHighImpactAction returns allowed, runTerminalCommand recurses with `mode: 'user'`; evaluateTerminalCommandPolicy returns allowed immediately for mode 'user' (terminal-command-policy.ts:2100). So approving e.g. a `git push` in a read-only-profiled agent turns that exact string into a full-access execution: any `; curl ... | sh` composition allowed by the classifier target is no longer checked by profile rules. This is a TS logic issue (fixable in TS), but it illustrates why a capability-based sandbox matters: with SB-1, an approval would grant one narrow capability (e.g. network to github.com for this exec) instead of flipping to unrestricted.
- **Fix:** TS now: re-run with the original mode and a one-shot approval token that exempts only the classified action from the harness check, keeping profile policy. Native later: approval receipt maps to an added capability in the sandbox profile (net host allowlist entry, one extra rw path) for a single exec.
- **Evidence:** run-terminal-command.ts ~330-360: `return runTerminalCommand({ command, ..., mode: 'user', permission_profile, ... })` inside authorizeHighImpactAction(...).then; terminal-command-policy.ts:2100 `if (params.mode === 'user') return { allowed: true }`.

## [MEDIUM] security — sdk/src/tools/browser-logs.ts:572 — SB-7 Headless Chrome launched with --no-sandbox and an unauthenticated TCP CDP port; run it inside the native sandbox and use --remote-debugging-pipe
- **Risk:** ensureBrowserSession spawns Chrome with `--no-sandbox` and `--remote-debugging-port=<port>` (:564-577). Chrome's own renderer sandbox is off while it loads agent-chosen (potentially hostile) pages, and any local process/user can attach to the CDP port and drive the browser (read cookies from the temp profile, navigate to file://). No outer confinement exists.
- **Fix:** TS-doable: switch to `--remote-debugging-pipe` (fd 3/4 CDP transport) and drop --no-sandbox where user namespaces are available. Native value: run Chrome under the SB-1 shim with a network egress allowlist (e.g. only localhost dev server for browser-logs testing) and an fs view limited to its userDataDir. Feature unlocked: safe 'open this untrusted URL' tooling and deterministic offline web testing (block all non-localhost egress so tests cannot hit prod).
- **Evidence:** browser-logs.ts:572 '--no-sandbox', :573 `--remote-debugging-port=${port}`, :563 userDataDir under tmpdir.

## [MEDIUM] security — common/src/util/redact-secrets.ts:15 — SB-8 Secret detection is 5 token regexes + 2 staged-diff regexes; embed a maintained scanner corpus (gitleaks/trufflehog in Go, or Rust vectorscan multi-pattern) for output redaction, commit gating and live verification
- **Risk:** TOKEN_SHAPES covers sk-, ghp_/gh*_, AKIA, Bearer (:15-21). validateStagedCommit checks only PEM headers and AKIA (run-terminal-command.ts:34). Missing: Slack/Stripe/Google/Azure/GCP SA JSON, JWTs, npm tokens, high-entropy strings, Anthropic keys (sk-ant- is caught by sk- only incidentally). Command stdout/stderr returned to the model is only stripColors'd (run-terminal-command.ts:609), redaction happens later at prompt level.
- **Fix:** Candidate: Go — gitleaks (library `github.com/zricethezav/gitleaks/v8/detect`, ~200 rules + entropy + allowlists) or trufflehog (800+ detectors with LIVE credential verification), built as a c-archive or sidecar; or Rust with `vectorscan-rs`/`aho-corasick` + regex-automata compiling the gitleaks TOML ruleset into one multi-pattern DFA. Feature unlocked: stream-time redaction of command output before it enters context or logs, pre-commit and pre-push gating with rule IDs, and 'this key is LIVE' verification (trufflehog) to prioritize. Cost: low-medium. Honest TS answer: the gitleaks TOML rules are mostly portable to JS regex, and throughput on 50KB outputs is fine in JS — the real gains from Go are the maintained detector corpus + verification, not speed.
- **Evidence:** redact-secrets.ts:15-21 TOKEN_SHAPES (5 entries); run-terminal-command.ts:32-35 SENSITIVE_STAGED_PATH / SENSITIVE_STAGED_CONTENT; :609 `str: stripColors(stdout)`.

## [MEDIUM] correctness — sdk/src/tools/run-terminal-command.ts:508 — SB-9 SYNC commands run on pipes with no TTY; interactive prompts hang to timeout and tools change behavior — PTY-backed exec with prompt detection
- **Risk:** stdio 'pipe' means isatty() is false: many CLIs switch output format, disable progress, or block on a password/`[y/N]` prompt reading from a pipe until the 300s basher default timeout (basher.ts DEFAULT_TIMEOUT_SECONDS). Output is colour-stripped by regex rather than interpreted, so cursor-movement redraws (progress bars) pile up as garbage in the 50K budget.
- **Fix:** Candidate: same Rust/Go PTY host as SB-5 used for SYNC exec (opt-in `tty: true`), with a vt100 screen model producing the FINAL rendered screen + scrollback instead of raw bytes, and a prompt detector (read quiescence + tcgetpgrp shows child waiting on terminal read + last-line heuristics) that returns `awaitingInput: {prompt}` early. Feature unlocked: agents see what a human sees, and hung-on-prompt becomes an immediate structured result instead of a 5-minute timeout. Cost: medium. TS: `script -q` wrapper gives a TTY cheaply on Linux/macOS (honest partial), xterm-headless can render; foreground-pgrp inspection needs native.
- **Evidence:** run-terminal-command.ts:508-513 `stdio: 'pipe'`; :566 STREAM_ACCUMULATION_CAP head/tail on raw text; basher.ts DEFAULT_TIMEOUT_SECONDS = 300.

## [MEDIUM] security — sdk/src/tools/terminal-command-policy.ts:1130 — SB-10 Hand-rolled shell tokenizers diverge from bash; use a real shell AST (mvdan/sh in Go->WASM, or tree-sitter-bash already shippable) for the lint layer
- **Risk:** At least five independent quote/escape scanners exist (tokenizeTmuxShellWords, splitReadOnlyShellSegments, scanActiveShellSyntax, extractSubstitutionsAndRemainder, quotedContentRanges) plus regex tokenizers `(?:[^\s"']+|"[^"]*"|'[^']*')+` in findTraversalPath/findOutsideAbsolutePath. They disagree with bash on ANSI-C quoting ($'..'), here-strings, brace expansion, arithmetic, `coproc`, aliases, and with each other. Every divergence is either a bypass or a false deny.
- **Fix:** Candidate: Go `mvdan.cc/sh/v3/syntax` (best-in-class POSIX/bash parser, compiles to WASM via TinyGo/GOOS=js, used by shfmt) — produces a full AST incl. word parts, redirects, substitutions; or Rust `brush-parser`. Feature unlocked: policy rules expressed over AST nodes (CallExpr name after wrapper-unwrapping, Redirect targets, CmdSubst bodies), plus human-readable 'why denied' pointing at the node, and a safe command rewriter (e.g. auto-add `--dry-run`). Honest: this is doable in TS today with web-tree-sitter + tree-sitter-bash (grammars already shipped for code-map); the language move is optional. It improves the lint layer only — it does NOT make the policy a boundary (SB-1 does).
- **Evidence:** terminal-command-policy.ts: tokenizeTmuxShellWords, splitReadOnlyShellSegments, scanActiveShellSyntax, extractSubstitutionsAndRemainder, quotedContentRanges; regex tokenizers in findTraversalPath and findOutsideAbsolutePath (:1928).

## [MEDIUM] state-mutation — sdk/src/tools/background-jobs.ts:363 — SB-11 Job durability lives in /tmp JSON + log files; a resident native job supervisor (subreaper) gives true reattach, exit codes and authenticated state across CLI restarts
- **Risk:** Cross-session recovery reads `openbuff-<jobId>.json` from os.tmpdir() (recoverBackgroundJob), with symlink/O_EXCL/O_NOFOLLOW hardening and an explicit unfinished HMAC item (SEC-5). A job whose CLI died can only become 'lost' (no exit code) because the new CLI is not its parent; output after the old drainer died is only recoverable by re-reading the file.
- **Fix:** Candidate: Rust or Go daemon (`openbuff jobd`, could be part of the prior report's `openbuff serve`) set as PR_SET_CHILD_SUBREAPER, holding pidfds and cgroups, exposing a Unix-socket API with peer-credential (SO_PEERCRED) auth; state in a private 0700 dir instead of shared /tmp. Feature unlocked: close the terminal, reopen, reattach to the dev server with full exit status and live stream; jobs shared safely between CLI, SDK host and editor. Cost: medium; daemon lifecycle/upgrade complexity. TS could run a daemon too (Bun process) — but subreaper/pidfd/SO_PEERCRED are not exposed to Bun, so the reliability properties need native code.
- **Evidence:** background-jobs.ts:363 sweepOrphanedJobFiles, recoverBackgroundJob status 'lost' promotion, :1291 SEC-5 follow-up, :177/ :719 tmpdir log fds.

## [MEDIUM] security — sdk/src/tools/terminal-command-policy.ts:2092 — SB-12 No isolation tier for untrusted repositories; microVM/container runner (libkrun, Firecracker, gVisor, Apple Virtualization.framework)
- **Risk:** 'full-access' profile and mode 'user' run directly on the host. Opening a cloned third-party repo and letting an agent run `npm install && npm test` executes attacker code with the user's full identity; the policy's only answer is to deny more commands.
- **Fix:** Candidates: Rust `libkrun` (lightweight KVM/HVF microVM, used by podman krun and krunvm, works on macOS Apple Silicon), Firecracker (Rust, Linux KVM), gVisor `runsc` (Go, user-space kernel), macOS Virtualization.framework (Swift) with virtiofs share of the project only. Feature unlocked: an 'untrusted repo' mode where the agent gets full-access INSIDE a disposable VM with only the project mounted (optionally via SB-3 overlay), network via the SB-2 proxy; snapshot/restore of the whole VM for branching. Cost: high; image management, boot latency (~100-300ms libkrun), per-OS backends. TS alternative: shell out to docker/podman — viable, but requires a user-installed daemon and gives weaker isolation than a VM.
- **Evidence:** terminal-command-policy.ts:2100 mode 'user' short-circuit; full-access profile skips all checks (`if (params.permissionProfile !== 'full-access')` blocks).

## [LOW] test-coverage — sdk/src/tools/run-terminal-command.ts:478 — SB-13 Command provenance: eBPF/fanotify/EndpointSecurity observation of files, sockets and execs each command actually touched
- **Risk:** There is no record of what a command read, wrote, executed or connected to; touchedPaths is a git-status approximation. Security review of an agent run cannot answer 'did this test contact the network' or 'did it read ~/.aws'.
- **Fix:** Candidates: Rust `aya` (eBPF, CO-RE: tracepoints on openat/execve/connect filtered by the job's cgroup id — pairs with SB-4), Linux fanotify (C/Rust) as an unprivileged-ish alternative for file access, macOS EndpointSecurity (Swift/C, needs entitlement) or `fs_usage`/DTrace; Windows ETW (Rust `ferrisetw`). Lower-privilege option: Landlock audit (kernel 6.x) and seccomp user-notify (seccomp_unotify) from the SB-1 shim to log/approve sensitive syscalls interactively. Feature unlocked: per-tool-call provenance ledger attached to receipts, live 'this command is reading ~/.ssh — allow?' prompts. Cost: high (privileges, kernel versions); ship as optional tier. TS: not possible (no syscall visibility).
- **Evidence:** run-terminal-command.ts:432/:478 listDirtyPaths before/after is the only attribution mechanism; background-jobs.ts dirtyBeforePaths/settlementTouchedPaths same approach.
