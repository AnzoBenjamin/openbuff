## Finding 1 — [HIGH] [Correctness/Perf] `isWhitespaceCodeUnit` wrongly classifies NEL (U+0085) as whitespace; ECMAScript `\s` does not match it — this is failing test 2

- File: `cli/src/utils/text-layout.ts:182` (`if (code === 0x85) return true`), with the false claim in the doc comment at `cli/src/utils/text-layout.ts:167-175` ("EXACTLY the ECMAScript `\s` set — `0x0085` (NEL) included") and `cli/src/utils/text-layout.ts:180-181`.
- Failing test: `measureLines whitespace class agrees with the sticky matchers > every classified code unit is tokenized on the run the class implies` (`text-layout.test.ts:1296-1348`). Reproduced: `mismatched = [{code: 133}, {code: 133}]` (133 = 0x85, present twice because the corpus ranges 0x00-0xA0 and 0x7F-0x9F overlap).
- Root cause (verified empirically, Bun 1.3.14): `/\s/.test('\u0085') === false` and `/\S/.test('\u0085') === true`. Per ECMA-262, `\s` = {0x09,0x0A,0x0B,0x0C,0x0D,0x20,0xA0,0x1680,0x2000-0x200A,0x2028,0x2029,0x202F,0x205F,0x3000,0xFEFF} — NEL (C1 category, not Zs/LineTerminator) is NOT in it. The author applied a Python/.NET/PCRE mental model where `\x85` is whitespace. An exhaustive sweep of the entire BMP confirms 0x85 is the ONLY divergence between `isWhitespaceCodeUnit` and `/\s/`.
- Concrete risk (PRODUCTION bug, not test staleness): the scan picks the sticky matcher from the classifier, so when a NEL starts a segment the classifier says "whitespace", `WHITESPACE_RUN_PATTERN` (`/\s+/y`, text-layout.ts:236,348-349) fails to match at that index, and the scan falls into its one-character fallback (`text-layout.ts:352`) — a slice + width measurement per character, the exact per-keystroke allocation the rewrite exists to remove, reachable from pasted content. It also breaks the module's core documented invariant ("the spans are identical by construction" with `split(/(\s+)/)`): `'ab'` yields 2 shipped spans vs 1 reference span (verified via the width-call seam). Row counts were NOT observed to diverge on any probe I tried (NEL measures 0 width via string-width, so wrap arithmetic coincides), so user-visible corruption is limited — hence HIGH, not CRITICAL. Note the OLD (pre-rewrite) `split(/(\s+)/)` code treated NEL as a word character, so the rewrite also changed tokenization semantics for NEL-leading segments.
- Suggested fix: delete `text-layout.ts:182` and correct the comments at `text-layout.ts:157-175` (NEL is NOT in ECMAScript `\s`). After removal the BMP sweep shows zero classifier/`\s` divergences and failing test 2 passes as written. (Alternative — make the matchers include NEL via `/[\s\u0085]+/y` — is wrong: it would diverge from the split reference the whole suite pins and from pre-change behavior, and would still fail test 2's `/\s/` oracle.)

## Finding 2 — [HIGH] [Test coverage] Failing test 3 asserts a factually wrong premise (NEL as a whitespace run under `\s`); it is mutually unsatisfiable with test 2

- File: `cli/src/utils/__tests__/text-layout.test.ts:1350-1367` (`a NEL in a pasted value is tokenized as a single whitespace run`), reproduced: `Expected: 3, Received: 1` for `'abcd'`.
- Root cause: the test's comment ("0x85 is whitespace under `\s`") is factually wrong in ECMAScript (see Finding 1). Expecting 3 spans (`'ab'`, `'\u0085\u0085'`, `'cd'`) requires the sticky matchers to treat NEL as whitespace — which contradicts test 2's oracle (`/\s/`) in the same describe block. With production as shipped the actual count is 1 (the sticky `/\S+/y` consumes the NELs into the word, verified), and it stays 1 after the correct fix to Finding 1. The two tests as written cannot both pass; the working tree is exactly the "mid-edit inconsistent" state the prior session warned about.
- Concrete risk: suite permanently red regardless of which production fix is chosen; a future editor "fixing" production to satisfy test 3 (adding NEL to the matcher class) would silently break reference-tokenizer parity.
- Suggested fix: after Finding 1's production fix, rewrite test 3 to pin the CORRECT property — NEL stays inside the surrounding word run (`expect(widthCalls).toBe(1)` for `'abcd'`, matching `split(/(\s+)/)`'s 1 span) — or re-target the "unusual pasted whitespace is a single run" intent at a code unit actually in `\s` (e.g. U+2028 LINE SEPARATOR, the closest NEL analogue). Also de-duplicate the corpus overlap at `text-layout.test.ts:1277-1279` (0x7F-0xA0 appears in both ranges; harmless but it double-reported 133).

## Finding 3 — [HIGH] [Correctness/Test] Failing test 1's expected-span formula (and its char-budget assertion) are stale: they count the newline characters the scan never slices — production matches the split reference exactly (723 = 723)

- File: `cli/src/utils/__tests__/text-layout.test.ts:604-648`, formula at `:625-632`, failing assertion `expect(slices).toBe(tokenCount)` at `:634` (reproduced: Expected 726, Received 723; MIXED_ASCII_PASTE is 1882 chars with exactly 3 newlines), masked second failure `expect(tokenChars).toBe(workload.length)` at `:644` (true shipped value 1879 = 1882 − 3; verified directly with the seam on `'ab\ncd'` → chars 4 of length 5).
- Root cause (TEST stale, production correct): the test formula adds `lineSegments.length - 1` ("plus one span per newline that ends a line", test:621-632). But the shipped multi-line-run walk (`text-layout.ts:364-391`) slices only NON-EMPTY line pieces between newlines — a pure `'\n'` or `'\n\n'` run slices zero strings, and the newline characters themselves are never copied into any slice. This exactly reproduces the pre-change reference's measured spans (`legacyMeasureLines`/`referenceMeasureLines` call `appendSegment(parts[i])` for empty parts too, and `appendSegment` returns early on `!segment` — text-layout.test.ts:796-799,1132-1135). I verified the correct oracle: `MIXED.split(/(\s+)/).filter(Boolean)` with newline-containing tokens contributing `token.split('\n').filter(Boolean).length` gives 723 — exactly what production emitted, and the width-call parity test for the same fixture passes at both 80 and 20 cols.
- Concrete risk: fixing only the span formula (as the diff's first failure suggests) still leaves line 644 red (1879 vs 1882); an implementer might then "fix" production by pointlessly slicing newline runs, degrading the exact allocation win the rewrite delivers.
- Suggested fix (test-side): derive the oracle from `split(/(\s+)/)` directly (multi-line tokens → non-empty `\n`-parts count), and change the char budget to `workload.length - (workload.match(/\n/g) || []).length`. Also fix the overclaiming production doc comment at `text-layout.ts:139-152` ("the characters copied equal the value's length") — newline characters are never copied; the seam honestly reports allocation volume, the doc mis-states it.

## Finding 4 — [MEDIUM] [Correctness] ASCII fast-path predicate `segment.length === segmentWidth` is also true for all-astral wide runs, so surrogate pairs are hard-wrapped as two 1-column units

- File: `cli/src/utils/text-layout.ts:287` (`if (segment.length === segmentWidth)`), comment at `:284-286` claims this identifies "an ASCII segment".
- Root cause: the predicate tests "code units == columns", which holds for pure-astral runs of 2-wide graphemes (e.g. `'👍👍'`: length 4, string-width 4 — verified). Such segments take the `cols`-subtraction path, emitting hard-wrap offsets at EVERY code-unit multiple, including indices inside surrogate pairs (break at offset 3 for `'😀😀'` @3 cols splits the second pair), and overcounting rows at narrow widths: `'👍👍'` @1 col → measured 4 rows vs 2 rendered (HEAD measured 3 vs 2 via its per-grapheme loop — same unsplittable-wide-char corner class, but the rewrite worsens the count and adds mid-surrogate break offsets used by the cursor-row accounting). The same copied predicate sits in both test references (`text-layout.test.ts:805`, `:1141`), so the oracle mirrors this bug instead of validating it.
- Concrete risk: wrong `totalLines`/cursor-row accounting for emoji-heavy input on very narrow terminals (cols ≤ 3); doc/comment mismatch.
- Suggested fix: gate the fast path on the module's existing `ASCII_PRINTABLE_REGEX.test(segment)` (true iff every code unit is 0x20-0x7E, where 1 unit == 1 column is actually guaranteed) instead of the length/width equality; apply the same change to both test references; add an astral entry (e.g. `'👍👍'`) to `TOKEN_SCAN_CORPUS` — the corpus currently has BMP CJK only (coverage gap, domain 7).

## Finding 5 — [LOW] [Performance/Test stability] Wall-clock ratio gates in the unit suite have thin headroom on loaded machines

- File: `cli/src/utils/__tests__/text-layout.test.ts:671` (`MAX_SHIPPED_TO_SINGLE_REFERENCE_RATIO = 4`; own comment records observed ratios up to 3.38 → ~18% headroom) and `:691` (`MAX_SHIPPED_TO_LEGACY_RATIO = 2`; recorded max 0.95), gates at `:1007` and `:1020`.
- Risk: CI runners are noisier than dev machines; a descheduled sample that survives the spread-based retry (`RETRY_ABOVE_SPREAD_RATIO = 3`) can still trip the 4x tripwire — flaky, not wrong. The deterministic work-volume and per-token-slice gates carry the real regression protection.
- Suggested fix: none required if CI proves quiet; otherwise raise the single-reference tripwire (it is explicitly an "order-of-magnitude" guard — 5-6x would still catch the ~2.4x-class regressions it names) or mark the ratio block as retry-tolerant.

## Finding 6 — [LOW] [Correctness, pre-existing] `measureLines` counts a phantom row for each unsplittable wide character at cols=1; `wrapTextToVisualLines` does not

- Files: `cli/src/utils/text-layout.ts:300-308` (per-grapheme `emitHardWrap` fires even when `acc === 0` and the char alone exceeds `cols`) vs `:443-450` (render wrap guards `filled.length > 0` and lets the line overflow instead).
- Verified: `'你'` @1 → measured 2 rows, rendered 1; `'你好'` @1 → 3 vs 2. Confirmed byte-for-byte against HEAD implementations — PRE-EXISTING, not introduced by this rewrite (only the astral variant worsened, see Finding 4). The module doc's "row count == rows the box renders" claim has this corner exception.
- Suggested fix: optional hardening — in the per-grapheme loop, only `emitHardWrap` when `acc > 0` (mirroring the render side). Low priority: requires a 3-column terminal to reach.
