## [HIGH] performance — packages/code-map/src/parse.ts:145 — Serial per-file parse loop over up to 10k files: no parallelism, one file at a time through web-tree-sitter WASM
- **Risk:** First-time indexing of a large repo is strictly serial: each file's language-config await, fs read, WASM parse, and query captures run on one event loop, so a 10k-file repo pays the full parse cost sequentially. This directly gates user-visible time-to-first-index and forces the MAX_PARSE_FILES/MAX_TOTAL_PARSE_BYTES budgets (defaults 10k files / 500MB) to truncate coverage on monorepos — a feature-limitation, not just a speed issue: coverage gaps mean weaker repo maps and worse search recall.
- **Fix:** Native component opportunity (candidate: Rust): replace the parse core with native tree-sitter via a napi-rs/bun FFI shim, keeping the TS facade. Native grammars are ~2-5x faster than WASM, and rayon work-stealing over files (respecting the existing per-file/total byte budgets and fairParseOrder fairness contract) turns multi-minute first indexes into seconds. New feature unlocked: a first-class full-repo index on any large monorepo without budget truncation (skippedLanguages/skippedPrefixes coverage gaps disappear in practice).
- **Evidence:** getFileTokenScores (parse.ts:108-284) iterates fairParseOrder(filePaths) serially; each iteration awaits getLanguageConfig(fullPath) then parseTokensForScoring; budgets default to 10,000 files / 500MB total (lines 12-27). parseFile (parse.ts:642-668) does parser.parse + query.captures per file with no worker fan-out. languages.ts:7 imports from 'web-tree-sitter' and loadLanguage resolves .wasm assets (languages.ts:263-292).

## [HIGH] performance — packages/code-map/src/languages.ts:7 — web-tree-sitter WASM grammar ceiling: no native tree-sitter bindings, no incremental parse, no zero-copy node access
- **Risk:** The whole parse tier runs on web-tree-sitter WASM: grammar execution happens inside a WASM sandbox with JS-boundary crossings for every node access. Beyond the ~2-5x constant-factor slowdown, WASM mode blocks capabilities TS cannot reach from JS: native-memory tree cursors for structure.ts's deep AST walks, tree-sitter's incremental parsing (edit/reparse of changed ranges), and multi-core grammar instances without N WASM copies.
- **Fix:** Native opportunity (candidate: Rust with tree-sitter crates + per-language grammar crates): compile grammars natively, keep the .scm tag queries verbatim (tree-sitter query API is language-compatible), and expose symbols/callSites as a compact binary (flatbuffer/bincode) result. Unlocks: (a) incremental reparses via tree-sitter's edit API for true keystroke-grade live repo maps; (b) LSP-grade symbol graphs (hover-ready signatures, doc comments — structure.ts already extracts signatureText/docText/typeInfo, so the data model is ready) at full-repo scale.
- **Evidence:** languages.ts:7 imports Language/Parser/Query from 'web-tree-sitter'; UnifiedLanguageLoader.loadLanguage loads .wasm from pinned assets (languages.ts:263-292); parse.ts:642-668 calls parser.parse(sourceCode) per file. wasm-files.ts pins 14 WASM grammars. structure.ts (lines 726-940) walks the JS-wrapped tree node-by-node (namedChildren arrays) for symbols + call sites, the most object-churn-heavy path.

## [HIGH] state-mutation — packages/indexer/src/index-store.ts:1074 — Whole-artifact JSON store: every refresh rewrites metadata.json/chunks.json/semantic-vectors.json in full; no mmap, no incremental persistence, no B-tree
- **Risk:** The index is three whole-file JSON documents (metadata.json, chunks.json, semantic-vectors.json) rewritten atomically on every refresh. Every save serializes and fsyncs the ENTIRE index even for a one-file mutation delta; every load JSON.parses the entire artifact (including an 8MB-bounded chunk sidecar) before any query can run. JS strings double the memory footprint vs a binary layout, and there is no mmap or random-access path: TS has no practical way to build an mmap-backed, incremental, crash-safe B-tree/LSM store, which is why the code resorts to whole-file rewrites guarded by a hand-rolled flock emulation.
- **Fix:** Native opportunity (candidates: Rust + sled/redb for a persistent B-tree/LSM store, or embedded SQLite with FTS5 + vec0 extensions): store postings, graph adjacency, and vectors in an mmap-backed transactional store; the TS side keeps only the query facade. Unlocks: instant warm starts (no full-index deserialize), per-file incremental persistence (mutation deltas commit in O(changed files) instead of O(index)), and crash-safe transactions replacing the hand-rolled lock/reclaim machinery. SQLite FTS5 additionally gives a real BM25 lexical engine for free.
- **Evidence:** loadIndex/saveIndex (index-store.ts:102-199) parse/serialize the full MetadataIndex JSON per refresh; atomicWriteJson (index-store.ts:1074-1094) rewrites the entire file each save; loadChunkSidecar refuses >8MB payloads by parsing bytes (MAX_CHUNK_SIDECAR_BYTES, index-store.ts:467); saveSemanticVectors union-merges the whole vector cache JSON (index-store.ts:239-318). ~250 lines of withCacheLock/reclaimStaleLock/releaseOwnedLock (index-store.ts:757-1063) hand-implement what a native store does with one open() call.

## [HIGH] performance — packages/indexer/src/query.ts:417 — Lexical scoring is O(files × tokens × fields) substring scans with hand-rolled IDF; no inverted-index quality tier
- **Risk:** Ranking is a hand-rolled scorer over nested JS arrays: for each query token, scoreFile substring-scans the file's symbol/heading/concept/import/chunk arrays, and the IDF fallback re-scans every indexed file's fields per uncached token. Recall quality is bounded by substring semantics: no BM25 term frequencies, no phrase/proximity matching, no prefix or fuzzy matching, no positional postings. This is a hard search-quality ceiling that cannot be lifted by tuning constants in TS.
- **Fix:** Native opportunity (candidate: Rust + tantivy for BM25 lexical tier over path/symbol/heading/concept/import fields, kept behind queryIndex's existing API): postings with positions replace substring scans, BM25 replaces the hand-tuned field weights (DEFAULT_LEXICAL_WEIGHTS become optional boosts), and phrase/prefix/fuzzy queries become native. Unlocks: instant full-repo search at 100k+ files, fuzzy/typo-tolerant symbol search (Levenshtein in postings), and per-chunk-level retrieval (chunks already carry stableChunkId/hash) without O(files) cost — all impossible at this complexity level in TS.
- **Evidence:** querySearch (query.ts:224-322) iterates filesToScore and calls scoreFile per file; scoreFile (query.ts:417-557) loops tokens × {path, symbols[], headings[], concepts[], imports[], chunks[]} with .includes() per element; computeIdfForTokens (query.ts:573-613) falls back to scanning every file's fields when a token has no posting (fileContainsToken, query.ts:629-651). IDF/adjacency/fileType caches (idfCache, adjacencyCache, fileTypeSetCache) only soften, not remove, the linear scans.

## [MEDIUM] performance — packages/indexer/src/semantic.ts:63 — Cosine similarity over all vectors in scalar JS: linear-scan semantic search with no SIMD/ANN path
- **Risk:** Semantic search is a brute-force linear scan: every query computes cosine similarity against every file vector in scalar JS (1536-dim × 20k files = ~30M FLOPs per query plus object churn over number[] vectors stored in JSON). No ANN index, no SIMD, no f32 packing (JSON stores base-10 doubles). Fine at hundreds of files; at tens of thousands, queryBlended latency grows linearly and the semantic tier degrades exactly where it is most valuable.
- **Fix:** Native opportunity (candidate: Rust + usearch/faiss/hnswlib over a memory-mapped f32 vector file, or sqlite-vec): keep the EmbedFn boundary and embeddingHash cache contract verbatim, swap only the storage + search tier. Unlocks: (1) instant full-repo semantic search regardless of file count (ANN instead of linear scan); (2) chunk-level semantic retrieval — chunkSidecar already has per-chunk contentHash/qualifiedName, so per-chunk embeddings become affordable; (3) zero-copy query-time access to vectors via mmap. A pure TS optimization (f32 via WebAssembly SIMD) is the fallback but still caps at linear scan.
- **Evidence:** cosineSimilarity (semantic.ts:63-75) is a scalar JS for-loop; semanticSearch (semantic.ts:197-215) maps every FileVector to a cosine score, filters, sorts, slices; FileVector.vector is number[] (heap JS doubles, ~8 bytes + object header per component vs packed f32). buildFileVectors (semantic.ts:117-194) re-embeds only changed files (embeddingHash cache) — the cache design is sound and portable.

## [MEDIUM] performance — packages/indexer/src/file-walker.ts:341 — Serial directory walk rebuilds three ignore matchers per directory per walk; no parallel walker, no OS-level fs_events
- **Risk:** The walker is a serial async recursion: for every directory it constructs a fresh ignore() matcher from 3 awaited file reads (gitignore/openbuffignore/codebuffignore), then lstats each entry one at a time. On a repo with thousands of directories this is thousands of serialized syscalls and matcher rebuilds per walk, repeated on every refresh. TS's single-threaded fs means directory subtrees cannot be walked concurrently without worker_threads (poor fit for fs-bound fan-out).
- **Fix:** Native opportunity (candidate: Rust — ignore/walkdir/jwalk crates, which implement exactly these semantics in parallel with gitignore support): expose one walk() call returning a flat file manifest; keep the fairness (per-prefix caps, round-robin trim) in a thin layer. Unlocks: near-instant full-manifest walks enabling a background incremental indexing daemon (watch via native inotify/FSEvents/ReadDirectoryChangesW in the same component — impossible without native FFI from TS) and fresh-on-edit indexes instead of the current 5-minute MAX_INDEX_AGE_MS staleness window.
- **Evidence:** walkProjectDetailed (file-walker.ts:341-513) awaits walk(abs, matchers) per directory serially; directoryMatcher = ignore().add([...await loadDirectoryIgnorePatterns(dir), ...]) is rebuilt inside walk() for every directory visited on every walk (no cache in this path — only statProjectFiles caches matchers, file-walker.ts:191-263); loadDirectoryIgnorePatterns (file-walker.ts:533-540) reads 3 ignore files per directory; per-file lstat (file-walker.ts:435-447) is awaited serially.

## [MEDIUM] dependency-hygiene — packages/code-map/src/grammar-wasm-repair.ts:23 — Grammar supply chain: 14 pinned WASM checksums plus a third-party vendored gdscript asset; repair path exists only because parsing is WASM
- **Risk:** Grammar availability depends on 14 pinned sha256 WASM assets (tree-sitter-wasms 0.1.13) plus one vendored gdscript build fetched from a third-party GitHub raw URL (lusiem/code-atlas). The repair path (download → 20MB cap → sha256 verify → temp-file rename → re-verify at load) is a runtime supply-chain surface that exists ONLY because parsing is WASM-based; SDK consumers offline get no repair at all. Any native migration must account for this: today's pinning/checksum contract is a security control, and its tests (grammar-wasm-repair.test.ts) are the regression harness.
- **Fix:** Native migration note (candidate: Rust): tree-sitter language crates are compiled into the binary at build time — the download/repair path disappears entirely, the gdscript third-party dependency becomes a reviewed vendored crate, and checksum pinning shifts from runtime download-verification to build-time supply-chain attestation (cargo-auditable/crates.io provenance). This is a net supply-chain simplification, but the migration must preserve resolveGrammarWasmSource's contract that a load either matches a pinned digest or fails deterministically with a stated reason.
- **Evidence:** PINNED_GRAMMAR_ASSETS (grammar-wasm-repair.ts:23-89) pins 14 assets to sha256; MAX_WASM_DOWNLOAD_BYTES=20MB cap (line 115); repairGrammarWasm gated on process.env.CODEBUFF_IS_BINARY === 'true' (languages.ts loadLanguage); resolveGrammarWasmSource (grammar-wasm-repair.ts:319-400) re-verifies persisted bytes before load. wasm-files.ts:1-16 enumerates the 14 grammars.

## [HIGH] performance — packages/agent-runtime/src/util/token-counter.ts:46 — JS BPE tokenizer is the compaction-budget bottleneck: 100k-char cap, 20k sample extrapolation, and per-family fudge factors approximate what a native tokenizer computes exactly
- **Risk:** Token counting is pure-JS gpt-tokenizer BPE with documented pathological behavior: a ~5MB separator-free tool-result measured >2 minutes per encode (killing a 25-minute CI budget), forcing the 100k-char cap + 20k sample extrapolation. Fudge factors (1.35 Anthropic, 1.1 Gemini) are documented approximations that can flip compaction/eviction trigger decisions near boundaries. The 8-100KB uncached band re-encodes in full every call by design. All of this is compensation for not having a native tokenizer.
- **Fix:** Native opportunity (candidate: Rust tiktoken-core via napi/FFI — it is already the industry-standard Rust BPE with SIMD): exact per-provider tokenizer counts (o200k/cl100k/claude/gemini BPEs), ~GB/s throughput making the 8KB cache bound and the sampling path unnecessary, and no fudge factors. Unlocks: exact context-window budgeting (context-budget.ts ledger totals become provider-accurate), precise compaction triggers (no 1.35x over-trim on OpenAI, no late-trim risk on Gemini), and affordable per-tool-result token accounting at streaming granularity.
- **Evidence:** token-counter.ts:46 MAX_BPE_ENCODE_CHARS=100_000 with comment citing a ~5MB tool-result body measuring >2 minutes per encode (CI run 36063479106); BPE_SAMPLE_CHARS=20_000 extrapolation (lines 149-208); fudge constants 1.35/1.0/1.1 (lines 92-94) with rationale comments; IncrementalTokenCounter (lines 335-380) memoizes per-message counts to fix a formerly-quadratic loop (run-agent-step.ts audit comment at 1995-1999).

## [MEDIUM] performance — packages/agent-runtime/src/util/stream-xml-parser.ts:105 — Stream XML tool-call parser: per-chunk string concatenation, rescan windows, and char-by-char JSON brace balancing in JS
- **Risk:** The tool-call stream parser is a string-based state machine: every chunk allocates via indexOf scans, string concatenation of buffer+pending, filteredText += building, and char-by-char balanced-brace scanning with up to 32 speculative JSON.parse calls per completed call. The scan-budget design (MAX_TAG_TAIL_CARRYOVER) is already linear-overall, but constant factors are pure JS allocation churn on the hottest per-token path in the product. Tool execution also happens inline in the generator (await executeXmlToolCall), serializing tool latency against stream consumption.
- **Fix:** Native opportunity (candidate: Rust byte-level state machine using memchr/memmem for tag search — exact same state contract, testable against the existing fixture tests): zero-copy chunk scanning on bytes, SIMD tag matching, and simd-json-style parse of the tool payload. This unlocks the streaming UX features TS cannot sustain: (1) true token-by-token tool-call previews (tool name + args streaming into the UI before execution), (2) overlapping tool execution with stream consumption via a native side-channel instead of await-pausing the generator, (3) sub-millisecond parser overhead making per-chunk processing free even on very high-chunk-rate models.
- **Evidence:** parseStreamChunk (stream-xml-parser.ts:105-242) builds `scan = state.buffer + pending` and accumulates filteredText += per segment; findBalancedObjectEnd (stream-xml-parser.ts:420-456) is a char-by-char loop over text[index]; extractFirstJsonObjectCandidate (stream-xml-parser.ts:381-409) JSON.parses up to 32 balanced candidates; processChunk (tool-stream-parser.ts:182-234) awaits executeXmlToolCall inline, pausing stream consumption while a tool executes.

## [MEDIUM] performance — packages/agent-runtime/src/run-agent-step.ts:2089 — Agent loop token accounting: system+tools recounted per iteration, per-message JSON.stringify + JS BPE on every new or rewritten message
- **Risk:** Even with IncrementalTokenCounter, the agent loop re-counts system+tools tokens on the iteration path (run-agent-step.ts:2089-2093 and again at 2387-2388), and every new/rewritten message triggers JSON.stringify + full JS BPE (countTokensJson → countTokens). With the 1.35x-fudged counts feeding compaction and eviction decisions, estimator cost and estimator error both scale with transcript size, and the loop pays JSON.stringify of each new message twice (once for counting, once for the request path).
- **Fix:** Native opportunity (candidates: Rust tiktoken + simd-json via napi): per-message counts drop from ~ms to ~µs, making continuous budget tracking — including streaming-time estimation of in-flight assistant output — effectively free. Unlocks: real-time context-window meters in the TUI, proactive pre-emptive compaction triggered mid-stream (before the provider 400s), and per-tool-call cost attribution computed exactly rather than estimated.
- **Evidence:** run-agent-step.ts:2086-2098 re-runs countTokensJson(system) + countTokensJson(toolsForTokenCount) and rebuilds estimateContextTokensLocally inside the step loop; line 2387-2388 recomputes the same pair when tool definitions change; tool-stream-parser and eviction paths ({...message} rewrites) each force one fresh countTokensJson per rewritten message (token-counter.ts:344-357 WeakMap miss). context-budget.ts:69-135 measureBlock/applyMeasure call countTokensJson per prompt block, every step.

## [MEDIUM] test-coverage — packages/code-map/src/parse.ts:1 — Rewrite protection assessment: strong test harnesses exist for code-map and indexer, but they pin behavior, not performance; WASM pinning is the tightest constraint
- **Risk:** The two highest-value rewrite targets (code-map parse tier, indexer store/query tier) are leaf packages with substantial protection: code-map has integration/parse/languages/wasm-dir/all-language-wasm/grammar-wasm-repair/incremental-parse/structure tests, and parse.ts's buildTokenCallers cross-language contract is explicitly pinned by BOTH code-map tests and the indexer's call-navigation suite; the indexer has query/query-quality/retrieval-quality/call-navigation/index-store/index-manager/p8-lite/m7-regression suites including a mean-reciprocal-rank quality harness (evaluateQueryIndexQuality). agent-runtime has tool-stream-parser, stream-xml-parser, token-counter, context-budget, and stream-parser abort/parallelism/reasoning suites. The gap: no benchmark/golden corpus pins parse THROUGHPUT or index-build latency, so a native rewrite is behavior-safe but not performance-regression-safe, and the WASM pinning tests would be obsolete rather than ported if grammars move to native crates.
- **Fix:** Rewrite plan (recommended order by test protection × payoff): (1) query/lexical tier → Rust/tantivy behind queryIndex API (best-protected: query-quality/retrieval/call-navigation suites act as golden MRR + behavioral harnesses); (2) index store → Rust/redb or sqlite FTS5 (index-store.test.ts pins lock/reclaim/CAS semantics — port these tests verbatim); (3) parse tier → native tree-sitter (parse.test.ts + incremental-parse.test.ts + all-language-wasm.test.ts define the contract; WASM-specific tests become obsolete by design). The agent-runtime stream/token paths are thin, hot, and exactly pinned — ideal candidates for a later, surgical napi module.
- **Evidence:** Test files located via discovery and confirmed by read_files referencedBy maps: packages/code-map/__tests__/{integration,parse,languages,wasm-dir,all-language-wasm,grammar-wasm-repair}.test.ts and src/__tests__/{incremental-parse,structure}.test.ts; packages/indexer: query.test.ts, query-quality.test.ts, retrieval-quality.test.ts, call-navigation.test.ts, index-store.test.ts, index-manager.test.ts, index-manager-semantic.test.ts, p8-lite.test.ts, p8-degraded-delta.test.ts, file-walker.test.ts, m7-regression.test.ts; agent-runtime: tool-stream-parser.test.ts, stream-xml-parser.test.ts (util/__tests__), token-counter.test.ts, context-budget.test.ts, stream-parser-{parallelism,reasoning,abort}.test.ts, xml-tool-result-ordering.test.ts.

## [MEDIUM] api-contract — packages/indexer/src/index-store.ts:757 — Hand-rolled cross-process lock + in-process singleton registry exists because TS has no native store/daemon; a native owner collapses this complexity and enables a background indexing daemon
- **Risk:** Because TS has no cheap cross-process shared-state primitive, the codebase hand-rolls a lock protocol (owner token, heartbeat, dead-pid probe, rename-verified reclaim) and a singleton registry with detached-instance forwarding and epoch mirroring — hundreds of lines whose entire purpose is to emulate 'one authoritative index owner'. This machinery is itself the main source of documented reliability findings in the package. A native component changes the API surface opportunity: a resident daemon owning the index eliminates the multi-writer problem by construction instead of by protocol.
- **Fix:** Native opportunity (candidate: Rust daemon — a long-lived background process owning the store, exposing a local IPC/Unix-socket API mirroring IndexManager's public methods): the daemon makes the singleton/lock machinery unnecessary (one owner process), enables fs-events-driven incremental reindex between agent runs, and serves queries to the CLI, SDK, and editor extension from one shared warm index. TS-side IndexManager keeps its exact API as a thin IPC client, so cli/sdk call sites are unchanged.
- **Evidence:** withCacheLock (index-store.ts:757-884) with heartbeat/token-verify/rename-verified reclaim; IndexManager detached-instance forwarding (index-manager.ts:153-288, markStale/markPathsChanged/forwardPendingMutationsTo with epoch-mirror invariants documented against six named reliability findings); snapshot pinning in queryBlended (index-manager.ts:470-562). All exist to make one JSON-directory shared safely between ad-hoc in-process singletons.

## [MEDIUM] correctness — packages/code-map/src/parse.ts:513 — Cross-package semantic contract: buildTokenCallers caller-edge rule is pinned by two suites in different packages and must survive any language migration of either side
- **Risk:** The same-language-only caller-resolution rule (M4-S6) is documented in parse.ts as pinned simultaneously by code-map's buildTokenCallers tests and the indexer's call-navigation suite ('does not create cross-language raw-name call edges'). A rewrite of either side in another language must preserve this exact semantic, and the language-family mapping itself is triplicated (getLanguageFamily in parse.ts, getLanguageTag in structure.ts, languageTable extensions in languages.ts) — drift risk a polyglot split amplifies.

- **Evidence:** buildTokenCallers comment (parse.ts:513-522): 'This contract is pinned by both code-map's buildTokenCallers tests and the indexer's call-navigation suite (does not create cross-language raw-name call edges)'. Same mapping duplicated in structure.ts:298-316 (getLanguageTag) and languageTable (languages.ts:59-130); fairParseOrder (parse.ts:558-575) and the walker's per-prefix round-robin (file-walker.ts:479-507) implement parallel fairness invariants.

## [MEDIUM] security — packages/code-map/src/grammar-wasm-repair.ts:319 — Pinned-checksum verification chain is a security control whose semantics must be preserved (or made build-time) in any parser migration
- **Risk:** resolveGrammarWasmSource is the trust boundary between downloaded grammar bytes and parser execution: candidate files are sha256-verified against pins before load, repaired bytes are re-verified post-write, downloads are capped at 20MB and hash-verified before persistence. A native-language migration that replaces WASM loading (e.g. dynamic native libraries) must reproduce or eliminate this verification chain; a naive port that loads native code without the equivalent pin would upgrade the failure mode from 'bad parse' to 'arbitrary code execution'.
- **Fix:** For a native migration: replace runtime download with build-time-vendored native grammar crates (removes the network path and this control becomes build-time attestation), or if any download remains, replicate the full pin-verify-temp-rename-reverify sequence in the native component and port grammar-wasm-repair.test.ts's scenarios (retry/backoff/cap/mismatch/re-verify) to the new seam before deleting the TS path.
- **Evidence:** repairGrammarWasm: 3 attempts × 30s timeout, Retry-After honoring + jittered backoff (computeRetryDelayMs, grammar-wasm-repair.ts:199-208), sha256 mismatch fails immediately without retry (grammar-wasm-repair.ts:281-287), verified bytes persisted via temp+rename with 0o600/0o700 modes (grammar-wasm-repair.ts:300-317); resolveGrammarWasmSource re-reads and re-hashes the persisted file before returning it (grammar-wasm-repair.ts:368-386).
