# N03: Plan mode is read-only (receipt)

**Status:** implemented. MCP/custom tools in plan mode are not covered (see "Not done").

## How plan mode is identified and propagated
- The root plan template (`base2-plan`, built by `createBase2('default', { planOnly: true })`) carries `programmaticConfig.planOnly: true`. The bundled CLI copy carries it too.
- Lineage is carried on each agent's template. `inheritPlanLineage` (new, in `packages/agent-runtime/src/tools/plan-mode-guard.ts`) is the one derivation. It is called from `deriveSpawnTemplateCapabilities`, so it covers `spawn_agents` and `spawn_agent_inline`, and from the journal-replay re-drive in `run-agent-step.ts`, which used to re-fetch the raw registry template and lose the lineage. The derivation marks the child `planOnly`, removes plan-refused tools from its `toolNames`, and sets its terminal profile to `read-only`. Grandchildren inherit through the derived parent.
- Every native tool call is checked in `executeNativeToolCall` (`tool-executor.ts`) by `checkPlanModeToolCall`. The check sits before the tool-list filter, so `handleSteps` calls, which skip that filter, are checked too.

## Decisions to review
1. **`write_audit_findings` is allowed in plan lineage, alongside `create_plan` and `update_plan_status`.** This departs from the two-tool list in the brief.
   - Why: plan mode is built to run broad audits. The plan-specific tail in `base2.ts` reads "In plan mode, do not implement — translate the findings into the durable plan packet". `agents/guides/broad-audit.md` requires general-agent shards to persist findings with `write_audit_findings` to get `structuralReceipt`s.
   - Safety: the tool writes only the runtime-derived path `.agents/sessions/<slug>/findings/<shard>.md`, never project source, which is the same class as plan artifacts.
   - Refusing it would make every plan-mode audit fail and would drop `general-agent` from plan mode.
   - To revert, move it to `PLAN_MODE_REFUSED_TOOL_NAMES`.
2. **`run_terminal_command` is not refused in plan lineage. It is clamped to `read-only` and enforced.** Basher stays spawnable for inspection.
   - Limitation: the `read-only` policy is lexical. It still allows `bun test`, `node -e …` and `python3 script.py`, which can write files. Only the OS sandbox (B21) closes that gap.
3. **Which declared profiles bind in execute mode, which is the B19 change.**
   - The SDK keeps the host execution context, which still selects sandbox, network and landlock. A declared `read-only` or `workspace-write` profile is added as a second policy check: the command must pass both.
   - I chose not to narrow the context profile itself, because on native backends that would also switch network to deny and enable landlock for basher. That would break normal execute work such as `npm install` and `curl`.
   - Effect on execute-mode basher and browser-use (`workspace-write`): they now refuse absolute paths outside the project (`cat /etc/os-release`, `~/...`), `../` that escapes the project, `bash -c`/`eval`, `printenv`/env dumps, `sudo`, `apt`, and force pushes. In-project work still passes: `bun test`, `git commit`/`push`, `npm install`, `rm -rf node_modules`, `sed -i`, `/tmp` reads and `curl`. I measured this with `evaluateTerminalCommandPolicy`. The read-only specialists (`integration-agent`, `performance-specialist`, `incident-coordinator`, `release-manager`) now run read-only.
   - Kept on current behaviour (host profile only): agents with no declared profile (base2-execute-plan, general use, custom agents) and the task-specific profiles `git-commit`, `dependency-mutation`, `tmux-test`, `validation-diagnosis` and `librarian-read-only`. Their policies depend on SDK flows (owned-path staging, fixtures, repro directories) that their agents were never run against. That matches the Accept clause, which names only read-only and workspace-write. **B19's next renewal should record that it no longer keeps full-access for declared read-only/workspace-write agents.** I did not edit roadmap state files.
4. `kill_job` is removed from the plan root's surface, because the root starts no jobs. For plan-lineage children it is allowed only for job ids the lineage recorded. The SDK registry's owner check still applies everywhere.
5. Refusals use the executor's existing error-chunk channel (`errorCode` field plus a prefix in `message`), the same channel as the other pre-dispatch refusals. Terminal denials put `errorCode` in the tool result value. `normalizeNativeToolOutput` returns the handler output unparsed, so the field survives. I did not add it to `terminalCommandOutputSchema`, which N06 owns.

## Not done / follow-ups
- MCP and custom tools are not gated in plan lineage. `loadAgentDefinitions` still merges `mcp.json` servers into `base2-plan`, and `executeCustomToolCall` has no plan check. Follow-up: refuse them in plan lineage unless the server marks the tool `readOnlyHint`.

- The task-specific terminal profiles do not bind yet (decision 3). Enabling them needs per-agent validation, starting with git-committer's owned-path flow.
- The kill_job ledger is in-process memory. After a process restart, a resumed plan lineage cannot kill jobs it started before the restart. It fails closed.
