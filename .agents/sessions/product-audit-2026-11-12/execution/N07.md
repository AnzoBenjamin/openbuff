## Changed files
- `sdk/src/error-utils.ts`
  - `RETRYABLE_STATUS_CODES` now includes 529.
  - New `PROVIDER_OVERLOADED_STATUS_CODE`.
  - `getErrorStatusCode` maps an error chain that contains `{ type: 'overloaded_error' }` (the SSE `event: error` on a 200 stream) to 529, so retry and failover treat both forms the same way.
- `sdk/src/impl/failover.ts`
  - `FAILOVER_ELIGIBLE_STATUS_CODES` now includes 529.
  - New session route health: `ROUTE_DEGRADING_STATUS_CODES` (401, 403), `createRouteHealthRegistry`, the process-wide `sessionRouteHealth`, `clearDegradedProviderRoutes`, and `orderModelsByRouteHealth`. The last one moves degraded routes behind healthy ones and keeps them as a last resort.
- `sdk/src/retry-config.ts`
  - `RETRY_AFTER_MAX_DELAY_MS = 120_000` and `RETRY_MAX_TOTAL_DELAY_MS = 180_000` are now part of `RETRY_POLICY`.
  - New optional `RetryPolicy.now` clock for HTTP-date hints.
  - The exponential backoff cap stays at 8 s.
- `sdk/src/impl/llm.ts`
  - `LlmHostDeps.routeHealth` is a new injectable seam.
  - The models to try are reordered by route health (`:1278`). The retry budget's primary is the first model actually tried.
  - `preferModelParam` is also set when a backup moves to index 0 (`:1363`). Without that, routing would send the request back to the primary.
  - On failover, a 401/403 marks the route degraded (`:2215`). The `provider_status` failover event now carries `providerId`, `apiKeyEnv` and `degraded`.
  - The retry event already carried `delayMs`, and it now carries Retry-After values up to 120 s.
- `sdk/src/provider-config.ts`: `isLocalHttpUrl` is exported and backed by `LOCAL_HTTP_HOSTNAMES` (`localhost`, `127.0.0.1`, `[::1]`, `host.docker.internal`; matched case-insensitively). Before, it compared against `::1`, which `URL.hostname` never returns.
- `sdk/src/index.ts`: exports `clearDegradedProviderRoutes`. This is a shared barrel; one line was added.
- `common/src/types/print-mode.ts`: `printModeProviderStatusSchema` gains optional `providerId`, `apiKeyEnv` and `degraded`.
- `cli/src/utils/sdk-event-handlers.ts`
  - The failover notice is now a persistent yellow status line that later retry and recovered events do not replace.
  - The notice reads: `Provider failover: <model> (<provider>) returned <status>; check <ENV>. Using <backup> for the rest of this session (/provider resets it).`
- `cli/src/commands/command-registry.ts`: `/provider` calls `clearDegradedProviderRoutes()` before it runs.
- `docs/configuration.md`: the failover section now covers 529, the session demotion, the Retry-After 120 s limit and the 180 s total limit.
- Tests:
  - `sdk/src/__tests__/provider-resilience-wire.test.ts` *(new)*.
  - `sdk/src/__tests__/provider-local-endpoint.test.ts` *(new)*.
  - `sdk/src/__tests__/fixtures/fake-llm-server.ts` *(new; shared with N01)*.
  - New cases in `sdk/src/__tests__/retry-config.test.ts` and `sdk/src/impl/__tests__/failover.test.ts`.
  - `failover-integration.test.ts` now resets the session registry in `afterEach`. Its 401 test otherwise demoted `local/primary` for the next test.
  - `cli/src/utils/__tests__/sdk-event-handlers.test.ts`: the coalescing test is updated for the persistent failover line, and there is a new 401 notice test.

The persistent notice text is checked in `sdk-event-handlers.test.ts` › "a 401 failover notice persists and names the status, provider and env var". |

"Inside the run deadline": the run's abort signal cancels the backoff wait, and `RETRY_MAX_TOTAL_DELAY_MS` caps each request at 180 s of waiting. Nothing in `llm.ts` reads the remaining deadline, so a wait longer than the time the run has left is cut off by the abort rather than skipped up front.
