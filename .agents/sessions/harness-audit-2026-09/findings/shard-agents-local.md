## [MEDIUM] correctness — scripts/tmux/tmux-cli.sh:110 — tmux-cli.sh start exits 0 with error text on stdout in the non-JSON passthrough branch, so wrappers adopt the error string as sessionName
- **Risk:** tmux-cli.sh captures tmux-start.sh output with '2>&1 || true' (:98); when the output does not start with '{' (tmux binary missing, crash before JSON print) it echoes the error text to stdout and exits 0 (:110-114). All four CLI wrappers parse run_terminal_command by trusting exitCode===0 && non-empty stdout, so the error string becomes sessionName; the agent then sends keys to a garbage session and reports misleading captures instead of entering the structured failure path. This bites exactly in the failure case the error handling was built for.
- **Fix:** Make tmux-cli.sh echo non-JSON output to stderr and exit 1 (or always emit the JSON envelope); additionally validate the parsed sessionName against ^[A-Za-z0-9_.-]+$ in the wrappers and route mismatches to the structured scriptIssues failure output.
- **Evidence:** tmux-cli.sh:98 'JSON_OUTPUT=$("$SCRIPT_DIR/tmux-start.sh" "$@" 2>&1) || true'; :102 'if [[ "$JSON_OUTPUT" == "{"* ]]'; :110-114 else-branch 'echo "$JSON_OUTPUT"; exit 0'; claude-code-cli.ts:59-71 'exitCode !== 0 || !stdout' else 'sessionName = stdout'; identical parse block codex-cli.ts:139-151, gemini-cli.ts:65-77, codebuff-local-cli.ts:60-72.

## [LOW] security — .agents/claude-code-cli.ts:135 — Session name from script output is interpolated into shell commands and coach messages without validation
- **Risk:** sessionName (stdout of tmux-cli.sh) is embedded unquoted into the stop command (claude-code-cli.ts:135-137, repeated in all four handleSteps) and into add_message coach text. tmux-cli.sh's sed extractor only excludes double quotes (:104), so $(), backticks, or ';' in a session name would execute in the wrapper's shell. Today the name is generated by tmux-start.sh, so exploitability is low, but createCliAgent already validates shortName for path use (create-cli-agent.ts:15-20) while sessionName gets no equivalent check — a defense-in-depth gap that compounds the passthrough bug.
- **Fix:** Whitelist-validate sessionName immediately after parsing (before any interpolation) and pass it as a single argument rather than building a quoted string; reuse the shortName-style regex guard for it.
- **Evidence:** claude-code-cli.ts:134-137 command concat; same pattern codex-cli.ts:214-217, gemini-cli.ts:141-143, codebuff-local-cli.ts:145-148; tmux-cli.sh:104 sed extractor; create-cli-agent.ts:15-20 shortName regex validation.

## [MEDIUM] api-contract — .agents/lib/cli-agent-types.ts:37 — CliAgentConfig.startCommand is a dead field; real start commands live duplicated as constants inside each handleSteps
- **Risk:** startCommand is declared (cli-agent-types.ts:37) and set in all four wrappers (claude-code-cli.ts:10 'claude --permission-mode acceptEdits', codex-cli.ts:81 'codex -a never -s workspace-write', gemini-cli.ts:10 'gemini --approval-mode auto_edit', codebuff-local-cli.ts:10 'bun --cwd=cli run dev'), but createCliAgent never reads it — a search of .agents shows only the declaration plus the four literals. Each handleSteps re-hardcodes the same command as a local START_COMMAND constant (claude-code-cli.ts:24, codex-cli.ts:101, gemini-cli.ts:27, codebuff-local-cli.ts:22). Editing config.startCommand silently changes nothing; the advertised config and the actually executed command (including security-relevant approval flags) can drift apart.
- **Fix:** Either make handleSteps read the serialized config (inject config JSON via an add_message and parse it — the pattern the inline comment hints at) or delete startCommand from CliAgentConfig and make each file's local constant the single documented source of truth.
- **Evidence:** cli-agent-types.ts:35-37; create-cli-agent.ts:1-86 contains no reference to startCommand; code_search 'startCommand' in .agents returns exactly the four config literals plus the declaration; duplicates at claude-code-cli.ts:24-26, codex-cli.ts:101-103, gemini-cli.ts:27-29, codebuff-local-cli.ts:22-24.

## [LOW] correctness — .agents/lib/create-cli-agent.ts:72 — Session start/parse/failure/cleanup handleSteps logic is copy-pasted verbatim across four agent files
- **Risk:** ~100 lines of handleSteps (prep add_message, tmux start, JSON parse, failure set_output, session announcement, STEP_ALL, stop) are duplicated nearly verbatim in claude-code-cli.ts:14-137, codex-cli.ts:101-217, gemini-cli.ts:20-143, codebuff-local-cli.ts:14-148, differing only in constants. The comment at create-cli-agent.ts:72-75 acknowledges the context-pruner pattern ('constants must be inside handleSteps since it gets serialized via .toString()'), but any bugfix (e.g. the parse bug in the tmux-cli.sh contract) must be applied four times and will predictably miss one. modeDescriptions are likewise duplicated between create-cli-agent.ts:20-23 and cli-agent-prompts.ts getSpawnerPrompt with different wording.
- **Fix:** Export one shared generator factory (e.g. makeCliHandleSteps(cliName, startCommand, {skipPrep})) from lib/ and have each file spread it into its definition; the serialization constraint can be satisfied once, in one place, by embedding the config values as literals in the factory body.
- **Evidence:** create-cli-agent.ts:72-75 NOTE comment; parse blocks at claude-code-cli.ts:44-104, codex-cli.ts:124-184, gemini-cli.ts:50-110, codebuff-local-cli.ts:44-104; modeDescriptions create-cli-agent.ts:20-23 vs cli-agent-prompts.ts getSpawnerPrompt modeDescriptions.

## [MEDIUM] error-handling — .agents/claude-code-cli.ts:133 — tmux session cleanup only runs if the generator finishes; aborts orphan tmux sessions and the Openbuff dev server
- **Risk:** The 'tmux-cli.sh stop' yield sits after 'STEP_ALL' in each generator (claude-code-cli.ts:132-137, codex-cli.ts:212-217, gemini-cli.ts:138-143, codebuff-local-cli.ts:143-148) with no try/finally. If the sub-agent errors, is cancelled, or the generator throws mid-run, the tmux session — and for codebuff-local-cli the 'bun --cwd=cli run dev' server — is left running with nothing to reap it. Repeated failures leak sessions and can exhaust tmux sockets or hold the dev port.
- **Fix:** Wrap the post-start body in try/finally so stop always runs, and/or have the runtime treat tmux-test sessions as leased (auto-stop on agent exit); at minimum document the leak path in the spawner prompt so parent agents clean up.
- **Evidence:** claude-code-cli.ts:132-137 (yield 'STEP_ALL' then stop, no try/finally); codebuff-local-cli.ts:22-24 starts 'bun --cwd=cli run dev' in the same lifecycle; no 'finally' appears in any .agents/*.ts file.

## [LOW] api-contract — .agents/lib/cli-agent-schemas.ts:58 — Structured output schema has no size bounds on capturedOutput, results, or reviewFindings
- **Risk:** outputSchema types capturedOutput as a plain string with no maxLength (cli-agent-schemas.ts:70-74) and results/reviewFindings as unbounded arrays (:54-77, :105-135). In structured_output mode a single verbose terminal capture — the prompts explicitly schedule 60s review captures — can dominate the parent's context or blow structured-output limits; 'Relevant output captured from the CLI' and the instruction that captures MUST be included are the only soft constraints.
- **Fix:** Add maxLength hints (e.g. 4000-8000 chars for capturedOutput) and maxItems for arrays, plus an output instruction: 'quote at most the relevant viewport slice; never paste full captures'.
- **Evidence:** cli-agent-schemas.ts:54-77 results, :70-74 capturedOutput, :105-135 reviewFindings, :136-144 required list with no size bounds; getInstructionsPrompt 'Always include captures in your output'.

## [LOW] security — .agents/codex-cli.ts:81 — Inner CLI sandboxing rests on per-CLI flags with no wrapper-side validation and no filesystemScope
- **Risk:** The wrappers' own terminal profile is the runtime-enforced 'tmux-test' (create-cli-agent.ts:50), but the spawned CLIs edit the real workspace under their own flags: 'claude --permission-mode acceptEdits' (claude-code-cli.ts:10), 'codex -a never -s workspace-write' (codex-cli.ts:81), 'gemini --approval-mode auto_edit' (gemini-cli.ts:10). The permissionNote strings forbid bypasses, yet nothing validates that the start command still carries the restrictive flags, and the definitions do not use the available filesystemScope field (agent-definition.ts) to fence their own tools. A future 'speed up the CLI' edit to a START_COMMAND constant would silently widen what the inner agent can do.
- **Fix:** Assert at definition-build time that each start command matches an expected allowlist regex (e.g. /acceptEdits$/, /-a never -s workspace-write/, /--approval-mode auto_edit/) so flag removal fails fast, and add filesystemScope write fencing where the wrapper's own tools only need read/search.
- **Evidence:** codex-cli.ts:81-84; claude-code-cli.ts:10-13; gemini-cli.ts:10-13; codebuff-local-cli.ts:10; agent-definition.ts filesystemScope field (~:150-156) unused in all four definitions.

## [LOW] dependency-hygiene — .agents/notion-agent.ts:25 — Notion MCP server is npx-fetched at runtime; version-pinned but an undeclared node/npx runtime dependency
- **Risk:** Both notion agents spawn 'npx -y @notionhq/notion-mcp-server@2.4.1' (notion-agent.ts:24-27, notion-researcher.ts:32-35). The exact version pin is good, but npx resolves from the npm registry at agent start with -y auto-install, requires node/npx on PATH (declared in no package.json), and a failed or slow fetch surfaces as a generic MCP spawn failure. The supply-chain surface is whatever npm serves for that spec at run time within the pin.
- **Fix:** Document the node/npx prerequisite in the spawnerPrompt, and prefer a workspace dependency plus direct bin invocation (or a vendored install) so MCP startup is offline-deterministic and install-time is hermetic.
- **Evidence:** notion-agent.ts:23-27; notion-researcher.ts:31-35; no '@notionhq/*' entry in .agents/package.json or root package.json dependencies.

## [LOW] dependency-hygiene — openbuff.d.example/providers.json:152 — Duplicate provider entry: 'AGENT_ROUTER' mirrors 'agentrouter' with the same baseURL and key env but a different model list
- **Risk:** 'agentrouter' (apiKeyEnv AGENT_ROUTER_TOKEN at :128) and 'AGENT_ROUTER' (same env at :155) both point at https://agentrouter.org/v1 but advertise different model lists ('agentrouter' has gpt-5.5/claude-opus-4-6 etc.; 'AGENT_ROUTER' has glm-5.1/deepseek-v4-pro/deepseek-v4-flash). In an example config this teaches users to create alias providers, makes model resolution ambiguous (a model can exist under two provider names), and reads as leftover config rather than a curated example.

- **Evidence:** providers.json 'agentrouter' and 'AGENT_ROUTER' blocks (apiKeyEnv AGENT_ROUTER_TOKEN at :128 and :155, identical baseURL 'https://agentrouter.org/v1'); routes.json references only 'agentrouter/*' and 'iamhc/*' ids, never 'AGENT_ROUTER/'.

## [LOW] performance — .agents/lib/cli-agent-prompts.ts:3 — Capture artifacts accumulate across runs without retention guidance; per-run capture economy is enforced but cross-run growth is not
- **Risk:** Session docs direct every capture to debug/tmux-sessions/{session}/ (TMUX_SESSION_DOCS, cli-agent-prompts.ts:3-27) and debug/ is in active use at the repo root. The prompts are disciplined within a run ('Prefer at most 1-2 progress captures'; 'Prefer fewer, higher-value captures') but nothing prunes prior sessions, so repeated CLI test runs accumulate capture text files indefinitely, slowing the capture-dir reads the parent performs via read_files and inflating debug storage.
- **Fix:** Add a one-line cleanup instruction ('remove your session dir after reporting') and/or have tmux-stop.sh optionally rotate sessions older than N days; state the retention policy in TMUX_SESSION_DOCS.
- **Evidence:** cli-agent-prompts.ts:3-27 TMUX_SESSION_DOCS capture paths; getWorkModeInstructions 'Prefer at most 1-2 progress captures'; TMUX_DEBUG_TIPS (:29-34) lists only attach/list/view, no pruning.

## [LOW] correctness — .agents/codex-cli.ts:30 — Codex reviewType default is prompt-claimed but not schema-enforced; hardcoded arrow-key menu navigation is brittle to upstream changes
- **Risk:** extraInputParams describes reviewType as 'Defaults to "uncommitted"' (codex-cli.ts:92-96), but createCliAgent injects no default into the enum schema (create-cli-agent.ts:31-39 only spreads extraInputParams), so an omitted reviewType relies on the model inferring 'uncommitted'. The navigation recipe hardcodes that the /review menu opens with Option 1 selected and counts Down presses per reviewType (codex-cli.ts:41-47); an upstream menu reorder or a remembered-last-selection default silently reviews the wrong target.
- **Fix:** State the omission default explicitly in CODEX_REVIEW_MODE_INSTRUCTIONS ('if reviewType is not provided, treat as uncommitted'), and add a capture-then-verify step ('capture the menu, read which row is highlighted before pressing Enter') instead of blind Down counts.
- **Evidence:** codex-cli.ts:30-47 mapping and navigation; codex-cli.ts:88-96 param description 'Defaults to "uncommitted"'; create-cli-agent.ts:31-39 inputParams assembly with no defaults injection.

## [LOW] state-mutation — .agents/claude-code-cli.ts:134 — Session teardown runs as a hidden tool call, leaving the terminal lifecycle untracked in the transcript while the inner CLI mutates the workspace
- **Risk:** The final 'tmux-cli.sh stop' is yielded with includeToolCall: false (claude-code-cli.ts:134-138; same in all four files), so the command that kills the tmux session — and for codebuff-local-cli the dev server — never appears in the agent's message history or the parent-visible trail. Because the inner CLIs mutate the workspace during STEP_ALL, an auditor replaying the transcript sees workspace edits but never the terminal lifecycle; a misfired stop (wrong session per the unvalidated-sessionName finding) would also be invisible.
- **Fix:** Emit lifecycle commands with includeToolCall: true (they are one-line, low-noise) or summarize them in the final add_message; reserve hidden yields for genuinely noisy pollers.
- **Evidence:** claude-code-cli.ts:133-138; codex-cli.ts:213-217; gemini-cli.ts:139-143; codebuff-local-cli.ts:144-148 — all set includeToolCall: false on the stop command.

## [LOW] api-contract — .agents/lib/create-cli-agent.ts:26 — Hardcoded providerOptions.ignore: ['Amazon Bedrock'] is applied to every CLI agent without explanation or config escape hatch
- **Risk:** createCliAgent bakes 'ignore: ["Amazon Bedrock"]' into all four wrappers (create-cli-agent.ts:26-28). AgentDefinition.providerOptions.ignore is otherwise a user-controlled routing knob (agent-definition.ts providerOptions docs), and this blanket override wins over openbuff.json routing for these agents; nothing in the prompts, spawnerPrompt, or comments explains why Bedrock is excluded. Users routing everything through Bedrock see these agents fail differently with no diagnostic.
- **Fix:** Move the ignore list into CliAgentConfig (e.g. providerIgnore?: string[]) with a comment, or document the rationale in the spawner prompt; if it must stay global, state the reason inline.
- **Evidence:** create-cli-agent.ts:24-28; agent-definition.ts providerOptions.ignore doc block; code_search 'Amazon Bedrock' in .agents returns only this occurrence.

## [LOW] test-coverage — test/setup-scm-loader.ts:5 — Globally preloaded SCM loader is only exercised transitively; the languages test works around Bun .scm quirks instead of asserting the loader contract
- **Risk:** bunfig.toml preloads test/setup-scm-loader.ts for every workspace test run (bunfig.toml:9-11), and its contract (read .scm file, export content as default via loader 'object') is what packages/code-map/src/languages.ts:16-30 depends on. No test exercises the plugin directly; packages/code-map/__tests__/languages.test.ts:342-356 carries a workaround comment ('In Bun, .scm imports may resolve to a file path rather than content') and re-reads the file from disk to compare, so if the loader regressed to exporting a path, that test would still pass by re-reading — masking the regression for any other .scm importer.
- **Fix:** Add a focused test importing an .scm module and asserting the default export equals the file bytes; tighten the languages test to fail when import resolution returns a path instead of content.
- **Evidence:** test/setup-scm-loader.ts:4-15 (filter /\.scms$/, loader 'object'); bunfig.toml:9-11 preload; packages/code-map/__tests__/languages.test.ts:342-346 'In Bun, .scm imports may resolve to a file path rather than content' + disk re-read at :346.
