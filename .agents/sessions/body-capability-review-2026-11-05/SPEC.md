## Product and authority

The configured model reasons about the user's objective and chooses its strategy and actions. Openbuff supplies observations, effects, resource ownership, human controls, persistence, memory, coordination, interfaces and evidence. A host contract must work for a custom strategy as well as shipped base2; a prescribed reviewer/repair workflow does not substitute for task intelligence. Current configurable generators, native/custom tools and mode grants are substantial foundations (`packages/agent-runtime/src/run-programmatic-step.ts:401`; `sdk/src/run.ts:2406`; `common/src/tools/list.ts:90`, pair 10/12).

The CLI remains the principal everyday client. SDK, headless and ACP clients project the same session/run/action meaning. Local/BYOK routing and the user's explicit full-access choices remain supported. The shipped terminal handler deliberately uses full access (`packages/agent-runtime/src/tools/handlers/tool/run-terminal-command.ts:38`, pair 09); changing that preference is outside this plan. A narrower or enforced profile applies only when selected, with requested, available, active and enforced states reported separately. Results, byte preservation and ownership remain truthful in every profile.

One logical session authority owns `sessionId`, `runId`, `turnId`, `taskId`, `actionId`, attempts and terminal state. TypeScript owns model coordination and public contracts; a selected native service can own process/commit/journal/lease primitives through an explicit versioned interface. Clients and services do not mint replacement identities for an interrupted run. A fresh turn and an explicit fork have different recorded identities. Current main resume remints run identity and ACP drops executable state (`packages/agent-runtime/src/run-agent-step.ts:1963`; `sdk/src/serve/bridge.ts:754`, 05-F1, 05-F4).

### Repository backend and native transition

The C-owned SessionAuthority is the common identity issuer/registrar and run-terminal semantic owner. A native backend transactionally persists its tickets and validates admitted resource ownership; it does not run a competing task-success state machine. One physically bound repository control record selects backend (`ts`/`native`), monotonic epoch, migration phase/id, identity namespace, store schema and writer protocol. Proposed initial authority/store protocol is 1 with explicit version-1 compatibility; actual package versions/hashes are frozen before implementation tests. Unknown schemas/protocols refuse mediated writes.

Participating upgraded SDK/CLI broker/semantic mutations, transaction recovery, index/cache/graph and snapshot publication, checkpoint/journal/task-state writes and child-mediated commits use that single admission gate. Old-wire compatibility adapters participate only if their host adapter implements the epoch protocol; unaware unmodified binaries and arbitrary same-user/full-access shell/hook/MCP/custom effects cannot universally be fenced. They remain external effects with observed captured-basis/conflict/reconciliation limits. A native token proves admission for mediated operations, not universal exclusion of user filesystem writes.

During quiescence, new participating writes stop and existing admitted operations/children are drained or explicitly resolved under the verified OS-held repository gate. Unknown/living/unreconciled owners block activation. Imports use immutable copies and retain IDs/hashes/originals/uncertain conflicts, then selection activates by durable expected-epoch CAS. After native activation, daemon outage/version skew returns unavailable/recovery-required; there is no silent TS write fallback. Before activation and native effects, a verified staging import may be abandoned back to the unchanged TS epoch. After activation/native writes, this baseline refuses in-place downgrade or stale TS-snapshot restoration; a future reverse migration requires current-native export/quiescence and a new epoch.

The minimal baseline is M22-CORE after B04/B15/B21, limited to new job/journal/lease store/admission and fenced commit API on eligible fresh namespaces. Legacy transaction/recovery import is M22-TXN after accepted B05/B07. Production child ownership/journal migration is M22-CHILD after B16 and M22-TXN for its commits. The B22 card is accepted only after all three exact milestone receipts and the populated mixed-client cutover/outage/rollback matrix; baseline boot cannot accept the rollup. Detailed protocol, graph/ledger and commands are canonical in PLAN.md.

### Outcome model

An action receipt records `actionId`, `attemptId`, its captured basis and an outcome of succeeded, failed, refused, cancelled or uncertain, plus typed cause and confirmed/partial/unobserved effect evidence. Earlier errors remain in the ledger after recovery. Mutation receipt status describes the effect on bytes separately from the reason a rollback was attempted.

A run records its terminal reason: completed, failed, cancelled, budget exhausted, step exhausted, deadline exhausted or resource/cleanup failure. It also retains owned resources and their observed cleanup state. A detached job can outlive a completed turn only through an explicit session-owned handoff; that does not satisfy a selected termination limit. Task acceptance is accepted, rejected or unknown under a named oracle and observed scope/basis. Schema-valid output, a reviewer verdict or a zero exit alone does not imply objective completion. This repairs the actual distinctions lost in 03-F2, 06-F3 and 11-F1.

Must-pass controls: failed tool → successful recovery → accepted task with original failure retained; fatal generator → failed run; abort → cancelled run; hard deadline → terminated covered scope or failed limit acceptance; happy generator → completed run with independently evaluated acceptance. No blanket ban on accepting a recovered task.

### Limits, process ownership and spending

The process matrix is SYNC shell, BACKGROUND job, supervised child, configured hook, diagnostic/build/version/SCIP process, LSP, MCP stdio transport, Chrome, Blender/render helper and native role. B19 records each concrete production launcher and the common context; B20/B21/B25/B28/B33 attach the relevant lifetime proof. A missing launcher is an explicit coverage failure.

For enforced fixtures, the manifest selects deadline D=250 ms, TERM grace G=200 ms, KILL/reap grace K=200 ms and observation allowance J=1 s. Acceptance requires observed scope exit by D+G+K+J, closed/drained streams, no late owned marker writes and zero covered living descendants. These values define a fault fixture, not a product performance claim. Leader exit must not remove later KILL/cleanup authority. A still-living covered descendant fails the selected limit even if its PID is reported. Escaped/detached resources outside a cooperative process-group tier are reported as outside guaranteed coverage; OS-scoped guarantees require that tier's actual cgroup/subreaper/Job Object or equivalent test. Unbounded productive defaults remain selectable.

Provider requests have one retry owner, explicit finite attempts and cancellable bounded waits. Delivered content is never replayed by inference retry. Cost records retain provider/model/currency and observed, estimated or incomplete provenance, including failed/in-flight attempts. Local admission prevents new requests after the selected cap; remote in-flight cost can overshoot according to the declared reservation/calibration envelope. No exact remote billing guarantee follows from D41. Unknown usage cannot silently become zero cost (`sdk/src/impl/llm.ts:1876`, 02-F3).

The finite provider fault fixture selects three primary attempts, one backup, four total, exponential delay at most 200 ms, bounded Retry-After at most 250 ms, total retry waiting at most 600 ms and cancellation wait allowance 250 ms plus the observation grace. The attempt/reservation manifest is locked before execution. These are explicit test inputs, not universal provider service guarantees.

For a selected finite spending cap the default is **strict-capped**: a new attempt needs known currency/pricing and a justified conservative reservation bound; otherwise admission refuses. A failed/incomplete-usage attempt retains its held reservation across retry, children and restart, and releases it only after verified reconciliation. An explicitly selected **estimated-capped** policy records its estimator/bound/concurrency and degraded provenance; it never resets unknown cost to zero and discloses possible remote overshoot. **Uncapped** full-access execution remains selectable, with unknown cost reported. Explicitly configured zero-price local service is distinct from absent pricing. Observed charges above reservations are retained and stop further capped admission; no missing field refunds spend or authorizes unlimited attempts.

### Effects, journal and recovery

Every journaled action has a durable identity before dispatch, canonical input/basis hash, owner, adapter generation and replay policy. Confirmation is the observed effect/result persisted after dispatch. Test four crash points: before dispatch, during effect, after effect/before confirmation, and after confirmation. An effect ledger lookup uses original run/action identities and immutable bundle/schema versions.

| Action family | Confirmation/reconciliation basis | Automatic replay policy |
|---|---|---|
| Read/pure observation | Captured document/artifact hash and observation version | Safe re-observation; freshness differences are explicit |
| Broker edit/delete/move/group | Forward receipt, expected before/after hashes, contained path identity and transaction ownership | Replay only verified unapplied/idempotent state; divergence retains conflict |
| Child spawn | Child intent ID, durable owner/job record and own journal | Attach/re-drive the same verified child; no blind extra child |
| Declared idempotent external operation | Adapter-owned key plus documented query of that operation | Retry only after adapter confirms absent or safely repeatable effect |
| Arbitrary shell, MCP or custom effect | Declared adapter observation if available; otherwise no universal oracle | Remain uncertain and stop automatic rerun until evidence or explicit human resolution |

Recovery failure is nonterminal recovery-required state; successful paths can advance independently while unfinished paths remain inspectable/retryable. Physical path identity is checked during recovery, including replaced parents/symlinks. No universal exactly-once promise or heap snapshot is introduced. These rules directly address 05-F2 and 06-F4, 06-F5, 06-F12.

Automatic generator replay supports the maximal contiguous verified journal prefix whose bundle/runtime/contract/configuration hashes and ordered STEP/STEP_ALL/GENERATE_N/model/tool/host-callback inputs/results are complete and whose reconstructed yields/occurrences match. Replay-safe modules use immutable captured configuration and recorded reconstruction-relevant clock/random/environment/I/O inputs. Deterministic local generator state can be rebuilt from that prefix; arbitrary mutable module state, unrecorded direct I/O/nondeterminism, a missing record or changed bundle requires a declared tested reconstruction adapter or returns replay-unavailable. The host does not claim universal detection of arbitrary trusted JS dependencies: unknown eligibility remains unavailable. Such trusted/full-access modules still execute normally. Transactions requiring restoration consume accepted B07; native fence/child migration assurance waits its M22 scope.

### Memory and retention fixture

The deterministic fixture contains 200 chronological CLI messages of at most 1 KiB each, 30 tool results of 32 KiB each, five next-decision facts (value, negation, blocker state, source revision and next action), one explicit decision/rationale and four scoped procedures. It performs three real compactions, closes the store and continues in a fresh process. The next decision must receive the applicable facts and original result references/hash without knowing prior internal task IDs. Another-project and another-language procedures must remain inapplicable.

The five expected fixture facts are exact: `timeoutMs=1500` (changing it to zero fails); `forcePushMainRequiresExplicitRequest=true` with the preserved negation “do not force-push main without an explicit request”; `blockerId=contract-consumer-v2` with `status=open` until that consumer's oracle passes; `sourceRevision=order-schema@2`; and `nextAction=verify-order-contract-before-task-acceptance`. The explicit decision is “represent amounts in integer minor units,” with rationale “avoid binary floating-point drift at the shared contract.” They are fixture knowledge to retain, not new product-wide rules. The oracle compares their structured values/negation/status and decision/rationale, rather than merely matching a path or identifier.

Tool result identities are `result-000` through `result-029`. Each original is exactly 32,768 UTF-8 bytes, includes its distinct `RESULT-NNN` prefix and `TAIL-NNN` suffix, and has a precomputed content hash. The real evictor and later compactions create pointer-only copies under those same call IDs. Fresh-process exact-ID recall must return the original immutable body/reference and hash; a pointer, changed value or missing tail fails. Cold-turn selection also includes longer low-ranked distractors so retaining the critical facts cannot be satisfied by unsorted whole-record clipping.

Keep the current hot archive bounds visible: eight ordinary plus sixteen eviction snapshots, 200 messages per snapshot and existing per-part excerpt caps (pair 04). The protected memory block remains at most 12,000 characters; ranking chooses complete items before clipping. Rendering can keep a 100-message hot window while durable paging/export remains independent. Critical original results live as immutable artifact references rather than repeatedly expanded prompt text.

Each retention run declares rolling-by-quota/expiry or keep-until-explicit-deletion mode, prompt limit, aggregate archive/artifact byte quota, pinned-record policy and cutoff. The quota fixture selects 4 MiB to exercise eviction; that is fixture input, not a recommended universal storage budget. Rolling mode evicts disclosed unpinned records and retains retrievable originals while their references remain retained. A pinned set exceeding quota returns a typed retention-capacity state; it cannot promise indefinite complete storage under a fixed bound. Keep-until-delete mode is reported as unbounded storage. Prompt/data bytes, SQLite overhead, retained range and archive latency are measured separately. Identifier recall and factual-value/negation recall have distinct oracles (11-F7).
