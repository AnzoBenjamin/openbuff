# Requirements review

Reviewed 2026-11-06. Inputs: SPEC-DRAFT.md, ROADMAP-OUTLINE.md, CAPABILITY-RUBRIC.md, PLAN-NOTES.md and DELIVERY-CHECKPOINT.md; optional SCOPE.md and capability/finding indexes. No implementation source was reread. The optional indexes still contain pairs 01–09, so this review assesses requirement clarity rather than the substantive findings of later pairs.

The direction meets the user's macro/micro and two-part polyglot intent. Finalization needs the following specific edits. This is an advisory requirements review, with no final-plan approval decision.

## Required revisions

1. **Separate three outcome levels, including successful recovery.** SPEC-DRAFT.md:17 and :54 distinguish execution and task acceptance, but “failed external tool never produce successful machine evidence” can prohibit a valid task that recovers from a failed action. Define action outcome, run terminal reason and task acceptance independently; validation also needs an observed scope/basis. A failed/refused action retains its failure receipt. A fatal generator error, cancellation or hard-stop cannot become a completed run. A recovered task can be accepted by its task oracle without rewriting earlier failures. Require both a fatal-path fixture and a failed-tool→successful-recovery control.

2. **Bound hard-limit and cancellation claims.** SPEC-DRAFT.md:18 allows “explicitly reported still alive” to satisfy enforced resource limits. Distinguish guaranteed enforcement, cooperative limits, estimates and unavailable enforcement. A living descendant after a selected enforced deadline is a failed limit acceptance case; retain its owner and cleanup/reconciliation state. Define finite admission/retry/cancellation deadlines and the covered process platforms. For provider costs, preserve observed/estimated/incomplete usage provenance and declared possible in-flight overshoot; do not imply exact remote spending control where D41 only allows calibration. Full access remains usable, with truthful lifecycle and outcome reporting.

3. **Give uncertain external effects a terminal policy.** SPEC-DRAFT.md:20, :54 and :74 require reconciliation but do not define its completion condition. For each journaled action type, specify durable identity, the pre-effect capture point, the confirmation observation, and whether reconciliation/idempotent retry is supported. An arbitrary shell/MCP/custom effect may be unobservable after a crash. It must remain uncertain and stop automatic rerun until evidence or an explicit human decision resolves it. Test crash boundaries before dispatch, during effect, after effect/before confirmation, and after confirmation; do not promise universal exactly-once execution or introduce heap snapshots.

4. **Turn broad quantifiers into finite coverage sets.** SPEC-DRAFT.md:7–11, :22–28 and :75 leave “ordinary,” “every,” “representative” and “broad agency” open. Add a task-family map and an enumerated launcher/client/platform/language coverage matrix. For each body responsibility, show reachable capabilities, strengths, partial/unwired/absent/unknown gaps, affected task families and evidence limits. Missing frontier abilities belong in that inventory with explicit defer conditions; they need no new implementation commitment. An inventory of existing helpers alone cannot establish macro completeness. Each capability's micro explanation should link its limiting behavior, cause/evidence, proposed repair and declared quality envelope.

5. **Define retained-memory and measurement envelopes.** SPEC-DRAFT.md:21, :34, :73 and :78 require useful recall and bounded growth without stating the retention contract. Fix fixture size, compaction count, fresh-process behavior, expected next-decision facts/results, prompt/storage bounds and eviction/archive lifetime. Specify what remains retrievable when a bound is reached; do not combine indefinite complete retention with bounded total storage. For performance and live task quality, lock equivalent correct workloads, model/provider/configuration/version, repeated runs, budget, failure accounting, task oracle and reported uncertainty. Select thresholds from a recorded baseline or a concrete invariant, never an invented speedup.

6. **Make both language-cooperation proofs independently executable.** SPEC-DRAFT.md:25 and :60–66 plus CAPABILITY-RUBRIC.md's polyglot distinctions are sound but lack selected fixtures. Name an authored-body boundary fixture (TS host↔Rust role, with optional offline Python oracle) and a target-project contract-change fixture (specified schema/ABI producers, consumers and build/test targets). Declare operation tiers, position/byte encodings, versions, unavailable-tool behavior and installed assets. Include a concrete compiled/script target combination and an unknown-language generic control. The authored-body fixture must pass without Python; a target repository using Python does not change the body's optional-offline-Python decision. Preserve D29–D56's latest choices and state explicitly when an adapter uses a consumed tool.

7. **Specify promotion eligibility before any learning claim.** SPEC-DRAFT.md:27, :76 and ROADMAP-OUTLINE.md:13 need a locked held-out split, outcome eligibility/scoring for failed/paid/incomplete attempts, minimum evidence, paired comparison, language strata and rollback oracle. Separate zero deterministic regressions from statistically assessed task-quality non-regression; literal zero stochastic per-language regression is not a measurable promise. Record the confidence/acceptance rule before evaluation, include raw cost/artifact completeness, and block promotion when evidence is insufficient. User-selected configuration/prompt/router changes need an explicit application policy. Fixture/test state must be isolated from the existing shared lesson store identified in the audit; no live benchmark or learning experiment is required to complete this review deliverable.

8. **Remove dependencies that defer immediate truth/data fixes.** ROADMAP-OUTLINE.md:28, :34–46 and :53 currently conflict with its ordering. B2-T4 delays existing lock/CAS repairs until B4-T3; B7-T1 delays MCP result fidelity until the common execution context; B6-T1 waits for entire B1/B3/B4 groups despite the statement that measurement can start earlier. Split immediate TS correctness/outcome/fixture repairs from later native/context/full-workload integration gates. Keep D50/D51's minimal daemon shortly after the native adapter rather than behind an undefined whole-stage requirement. Replace B2/B1/B3/B4 dependencies with task IDs or explicitly defined readiness predicates. B1-T3 and B2-T1 are dependent next work, not initially ready tasks. Attach installed/native CI checks to affected tasks so B8 cannot become a postponed evidence phase.

9. **Make task cards and migration traceability enforceable.** ROADMAP-OUTLINE.md:18–61 is explicitly a skeleton. Each final task needs requirement/capability/finding IDs, current source anchors, smallest producer→consumer scope, owned files/shared-contract owner, precise prerequisites, language decision, positive and adverse acceptance cases, runnable verification command, expected artifact/exit/oracle, risks and stop/defer rule. Cover action/result propagation through SDK and CLI where relevant. Validate the graph and short ready queue mechanically. Give each of the 120 old declarations exactly one disposition row, with replacement task IDs or a reason for conditional defer/retirement; split rows can map to multiple new tasks. Preserve historical completion separately from current readiness.

10. **Keep delivery completion separate from repaired capability completion.** SPEC-DRAFT.md:82 and DELIVERY-CHECKPOINT.md's finish checklist should explicitly gate the planning artifact: all 13 durable pairs, final capability/findings digests, every directory disposition, evidence/source-snapshot limits, complete migration, independent review resolutions and valid links/commands. SCOPE.md still shows early planned/in-progress statuses and must be refreshed. Diagnostic probe passes demonstrate current defects; implementation acceptance remains prospective. Preserve existing user edits, local/BYOK and full-access decisions, and review-only scope. Stage publication-ready documents and probes as data before the final scoped publication escalation; maintain one canonical plan.
