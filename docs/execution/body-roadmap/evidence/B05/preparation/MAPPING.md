## Current contracts and observed gaps

- **Raw mutation identity:** `hashFileContent` / `FilesystemAuthority.snapshot` hash adapter bytes directly. `CodebuffFileContent` already supports strings or array-buffer views; conditional commit/delete/move accept exact expected hashes. Valid UTF-8 can remain a lossless string only if decoding preserves the BOM. These B03 byte guards must remain distinct from normalized matching hashes.
- **Normalized matching identity:** `getContentHash` hashes `normalizeLineEndings(content)`, which changes CRLF to LF but preserves lone CR. `getExactContentHash(string)` hashes UTF-8 encoding without EOL normalization. Current `cap.v3` authenticates a normalized range digest plus project/path/run, not a separate raw file/range digest. `readFilesEditAnchor` carries that normalized digest; `FileSnapshotV1.contentHash` is a different raw mutation snapshot role. Renaming or silently repurposing either hash would break consumers.
- **BOM:** SDK `decodeText` (`read-files.ts:281`) and transaction `readOptionalText` (`change-file.ts:998`) use fatal UTF-8 `TextDecoder` with its default BOM removal. Native byte-returning adapters therefore lose `EF BB BF`; string-returning adapters bypass the transaction decoder. The real broker compares raw bytes, so a reconstructed BOM-less preimage cannot authorize the BOM file and repeated reads repeat the mismatch. Read authority can still be minted from the normalized, BOM-less view. This is a basis/refusal defect, not evidence that every current BOM operation overwrites the file.
- **Unsupported text:** read_files rejects NUL-containing data and non-UTF-8. UTF-16 BOM checks exist, but NUL detection precedes them and can classify UTF-16 as binary. B05 need not add encoding support; preserve a truthful unsupported result and no edit grant. Whether byte-only delete/move must support arbitrary binary files is a root scope decision; the canonical B05 matrix explicitly requires supported UTF-8 byte cases.
- **Lines:** shared `getLineCoordinates` normalizes CRLF; `lines = text.split('\n')` retains a final empty entry. Empty content has zero visible lines but max capability line 1. Newline-terminated content has `visibleLineCount + 1` capability lines. `resolveLineRange` clamps the end to capability space. SDK range rendering instead strips the final empty entry and uses visible totals; whole-file reads and full visible-range reads both currently qualify as whole coverage. Preserve this distinction explicitly when mapping byte boundaries.
- **Offsets:** JavaScript string indices and transaction provenance offsets are UTF-16 code units. Read ranges are 1-indexed inclusive lines. There is no common UTF-16 ↔ UTF-8 ↔ raw/BOM/CRLF byte map. A normalized offset is not a raw byte offset; an astral character uses two UTF-16 units and four UTF-8 bytes. B06 must reject invalid/fractional/reversed/out-of-line positions; B05 should provide safe conversion primitives without accepting malformed boundaries or splitting a surrogate/UTF-8 sequence.
- **Localized edits:** transaction range and symbol branches splice and join the whole normalized snapshot, converting unrelated CRLF. Standalone `processStrReplace` already calls `restoreLineEndingsFromOriginal` at line 991; its `diffLines` restorer preserves unchanged original lines and modified-line EOLs, with mixed-EOL tests. Standalone rewrite_symbol delegates to str_replace. Separately, SDK `replace-range.ts` already walks raw UTF-16 line spans and preserves raw prefix/suffix and the ending terminator, choosing inserted EOL from the replaced span, then its ending terminator, then CRLF encountered up to the target. Its `expectedExactHash` closes raw drift between that pre-read and `changeFile`, but the original normalized cap.v3 does not bind raw drift before this pre-read. Reuse/centralize these proven paths, while fixing transaction range/symbol reconstruction.
- **Allocation:** `readNodeTextRange` retains `currentParts/currentBytes` for every line, including skipped lines, then `Buffer.concat`s a whole line before testing `maxBytes`. It has no signal argument. `readRange` bounds a byte request to 1 MiB and closes its file handle in finally. `readCanonicalSnapshot` stats first but calls unbounded `fs.readFile` for a file under 10 MiB; post-read size rejection cannot bound allocation if the file grew after stat. Current read_files oversized windows use a fixed 4 MiB byte budget; render limits are 10 MiB and aggregate schema content is 20 MiB. Returning less data does not prove bounded peak retention.
- **Metadata/coherence:** `CodebuffTextRangeReadResult` requires a numeric authoritative `totalLines`, with `complete` describing content coverage. The current adapter scans to EOF on a single stream but has no immutable-snapshot or drift check. `renderRangeItem` derives coverage from bounds and does not directly include `window.complete` in its final `complete` computation. A future truncated/early-stop result must not be upgraded to complete authority by that consumer.

## Minimal proposed shared implementation

1. Add a pure supported-UTF-8 document codec with separate exact source bytes/raw hash, BOM-preserving decoded source, normalized observation text/text hash, BOM/EOL metadata, and validated normalized UTF-16/raw UTF-8 offset conversion. Keep existing `getContentHash` semantics stable. For lossless text preimages, `TextDecoder(..., { fatal: true, ignoreBOM: true })` retains U+FEFF; an observation can omit it deliberately while storing its offset/metadata separately.
2. Provide one localized splice helper that maps accepted normalized ranges onto the captured original bytes and retains raw prefix/suffix. Extract/adapt the existing SDK `getRawRangeSpan` / `getRangeLineEnding` implementation rather than inventing a competing range EOL policy. Preserve the original BOM and unaffected terminators. Reuse the current str_replace restorer for its supported behavior; avoid introducing a whole-file normalization pass. Explicit whole-file replacement remains a separate intent from a localized edit.
3. Capture exact transaction preimages and expected raw hashes once; move/delete/rollback must consume that same basis and restore exact UTF-8 bytes/mode. Existing string contracts can remain lossless for supported UTF-8 if they carry BOM-preserving source text plus separate observation metadata. Use a richer snapshot callback only if required by the approved raw-grant design; do not change every callback to an object incidentally.
4. Fix line reading at accumulation time: count skipped newlines without retaining skipped text; retain at most remaining selected-output budget; stop retaining an over-budget line; avoid concatenating a rejected line. Make read cancellation reach the stream and settle after close. Expose measured retained-buffer accounting through a trusted adapter option/test seam; declare fixed chunk/high-water overhead. RSS is a separate measurement. Full-read stat/growth allocation needs a bounded descriptor reader or an explicit unbounded-adapter tier, not a post-allocation cap.
5. Propagate completeness and raw basis through native whole/range results, runtime token reminting, structural slices, post-edit grants, overrides and edit authorization. Do not fabricate a full raw basis from a truncated read or decorated display. Whole grants bind the observed whole file; scoped grants bind the exact observed raw slice and preserve existing unique reanchor behavior where that raw slice remains unchanged.
