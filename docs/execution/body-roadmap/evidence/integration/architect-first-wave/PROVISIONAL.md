## Demonstrated findings

1. **B30, medium: explicit empty error remains eligible in shared comparison consumers.** `evals/buffbench/statistics.ts:33` and `evals/buffbench/run-buffbench.ts:104` use `!run.error`. The repaired Codebuff runner correctly projects new empty errors to failed outcomes, but the comparison loader deliberately supports legacy records without runOutcome. Two such records per side with `error: ''` are accepted as two measured paired scores by `compareBuffbenchRuns`. Empty error presence is still an unsuccessful execution observation. Use an explicit absent/null policy, consistent in both selectors, and lock the shared selector and actual comparator. Existing no-error and measured-zero controls must remain eligible.
2. **B30, medium: aggregate cost can become nonfinite after finite input validation.** `scripts/compare-buffbench-runs.ts:154` adds costs with unchecked `reduce`. Two individually finite `Number.MAX_VALUE` costs return `Infinity` as each total, logged and serialized as `null`, while comparison succeeds. Validate the aggregate using checked finite addition or an equivalent shared finite operation, and retain an ordinary finite happy control.

`comparison-counterexamples.ts` invokes the actual comparison module and shared selector, not a replica. `comparison-counterexamples-command.json` records pinned Bun 1.3.5, a replacement environment, timestamps, exit, before/after source hashes and log hash. `comparison-counterexamples.json` records the healthy control, explicit-empty-error acceptance and nonfinite aggregate.
